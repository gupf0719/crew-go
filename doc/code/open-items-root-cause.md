## A、「接受」与「兑现」是两个动作，而校验只覆盖了前一个

**共同形状**：一个配置项/参数值被框架**接受**（不报错、甚至通过了枚举校验），但行为不兑现它
的名字，且**没有任何一条路径能让调用方发现**。

| 实例 | 接受了什么 | 实际做了什么 |
|---|---|---|
| `fork_with_context` | 通过枚举校验（未知值会响亮报错） | 走 `fork` 同一分支，无父历史复制，无 warn |
| skill frontmatter 未知键 | YAML 解析吃掉，`switch` 无 `default:` | 静默丢弃。`paths` 丢了 ⟹ skill 从「按路径条件激活」变成**无条件激活** |
| 记忆键相撞 | `WithStoreMemory` 正常配置 | 同一写入者被调多次且各自新建 child session ⟹ 序号重置 ⟹ 撞键 ⟹ 后写覆盖先写 |

### 为什么校验反而让它更糟

`fork_with_context` 这条最典型：**未知值响亮报错**（返 `SkillForkErrCode`）等于框架宣称
「我认得所有合法值」。业务写了一个**合法值**，收到的是「我懂了」的信号——那么它不兑现时，
业务连怀疑的理由都没有。

**全拒**（不认识就报错）和**全放**（都不校验，业务自己小心）各有各的道理；
**「校验了枚举，但某个成员不做它名字说的事」比两者都糟**。

### 判别式

写下一个配置项时问：**它被接受之后，有没有一条路径能让调用方发现它没被兑现？**

没有 ⟹ 这个配置项是个谎。修法有两个方向，选哪个是设计问题、但**不能两个都不选**：
- 兑现它（实现父历史复制 / 实现 `paths` 条件激活）
- 或在接受的那一刻出声（`switch` 补 `default:` 列出被丢的键；走到降级分支时 warn）

### 这一类的历史密度

本 session 修掉的同族还有：`WithStoreMemory` 配在成员上一条也写不进去、`Filter` 配了注入 0 条、
`listErr` 报上去那条路在它要救的形态上是死的。**加上表里现存的 3 条，一个月内至少 6 次。**

CLAUDE.md 已有的「借来的量」那节讲的是**近亲但不同**的病（X 被拿去做 Y、而 X 的名字里没有 Y
的意思）。这一类是**X 的名字里明明有 Y，只是没做**。建议并列成第二条。

## B、防线只有终点，没有中途

**共同形状**：某种资源被**连续**消耗，而防线是**一堵远处的墙**——撞上是终局失败，
中间没有任何减速带或提醒。

| 实例 | 连续消耗什么 | 墙在哪 | 撞上会怎样 |
|---|---|---|---|
| 重复工具调用 | ReAct 轮次 | `maxRounds` | 抛 `MaxIterationsError`，**模型没有自救机会** |
| 单次工具调用无超时 | 墙钟 | 只有 caller 的 ctx deadline | 整个 Run 被一个卡住的工具拖死 |
| 无每节点超时 + 一分支失败不掐兄弟 | 墙钟 | 同上 | 兄弟可以永远等下去 |
| 长跑工具无后台 job 协议 | 墙钟 | 同上 | 同上 |

### 代价的不对称性

**加中途信号很便宜**：同一调用重复 N 次就往对话里注入一条提醒；工具级 `WithTimeoutCause`
是标准库一行。**撞墙很贵**：`MaxIterationsError` 是终局的，整个 Run 的工作全废。

这个不对称本身就是论证——不需要「外部有我们没有」来支撑。

### 判别式

**这条防线撞上之后，还有没有恢复的余地？** 没有 ⟹ 它必须配一个更早、更软的信号。

## C、多件事同时发生，而报告只能报一件

**共同形状**：并发分支里发生了 N 件值得报告的事，而返回值只有一个 `error`。

| 实例 | 冲突 |
|---|---|
| 静态 fan-out 多分支同时失败 | 报哪个跨次不稳定（`assembleFrontier` 遍历 map 无序，实测 40 次 `A:36 Z:4`） |
| `ErrCheckpointNotResumable` 被兄弟的中断吞掉 | 中断优先 ⟹ 存档问题这一轮不可见 |
| `IsControlFlowSignal` 误判 | 认错误链上**任意位置**的 ctx 错，分不出是 caller 的还是业务后端内部的 |

### 这一类跟 A、B 不同：它目前没有好答案

`errors.Join` 试过并被否掉，理由是实测的：它让 `errors.Is` 的语义从**「这个错是不是 X」**
静默变成**「有没有哪个分支是 X」**——2 个可重试业务错 + 1 个 wrap 了自己下游 `DeadlineExceeded`
的分支，`IsControlFlowSignal` 返 true，那 2 个再也不重试。

**出路不在返回值上**：每个失败分支各自 fire 一次 `OnNodeEnd`（带分支身份）才是它们完整的
观测面。返回值那一个 error 只承担「这次 Run 成不成功 + 最该被看见的那个原因」。

**所以这一类的正确处置是：把「返回值只能报一件」写成明确契约，而不是继续想办法塞更多进去。**
表里那三条都该按这个方向重写，而不是各自找补丁。

## E、真正的元问题：判断状态的成本 ≫ 记录状态的成本

这一条不在表里，但它决定了表本身可不可信。

### 本轮实测的数字

**58 条里约 26 条状态不准（45%）**，而且分布不是随机的：

| 类型 | 条数 | 说明 |
|---|---|---|
| 早已修完还挂着 | 5 | 其中一条**在条目写完 2 天后**就修了 |
| 缺陷理由被实测推翻 | 4 | 一条的方向还反了（是**低估**不是高估） |
| 被低估 | 3 | 重复率 82%→94%、prompt 缺陷比写的更糟、零覆盖不是部分覆盖 |
| 数字/锚点漂了 | ~10 | 11 个调用点→2 个、候选 7 条→1 条、11 条→6 条 |
| **同一张表里自相矛盾** | 1 对 | 「已决」的决策记录，其决定性论证被本仓自己后来的改动推翻 |

### 成本比

- **写一条 backlog**：几分钟。
- **判定一条 backlog 是否仍成立**：读代码、跑测试、有时得写变异测试——本轮四个 agent 并发跑了约 4 小时。

**约 1:50。** 于是记录持续累积、判断持续被跳过。**而且它自我强化**：表越长，重新判定的成本
越高，越不会被判定，越不准。

### 我自己就是这个比值的直接后果

同一条（跨超步复用自填 `InterruptID`）我**连错三次**：照 backlog 报「开着」→ 匹配到一个
commit 改口「已修」→ 读到条目第三段又改回「开着」→ **实跑哨兵才发现真的已修**。

**三次都在读文档，没有一次去跑代码。**

### 可执行的推论

1. **backlog 条目必须带「怎么验」而不只是「是什么」**——一条能跑的命令 / 一个测试名。
   验证成本从「读代码推理」降到「跑一条命令」，1:50 才有可能变成 1:5。
2. **「已决」状态的条目要记下它的论证依赖了哪些事实**——那对自相矛盾的条目，正是因为
   论证里的四项事实中三项后来被改掉，而没人知道决策依赖它们。
3. **修完当场清**。本轮 5 条已修的没有一条是「忘了修」，全都是**修了但没回来清**。
