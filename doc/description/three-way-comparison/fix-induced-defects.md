# 修复引入新缺陷：成因分类与可机械化的部分（2026-08-25 调研）

**触发**：一个 session 内 7 次修复引出 7 个新问题。我先自己归纳了两个「形状」，调研**推翻了
其中一个**——那四条是四个不同的成因，把它们合并会让其中一条逃过一条已经写对的规矩。

## 一、七条链条与它们各自的真成因

| # | 发生了什么 | 真成因 | 已有规则覆盖？ |
|---|---|---|---|
| 1 | 抽公共判据时把 N 个中断合并成一批 ⟹ 业务用常量 ID 的合法 gate 被判协议违规、存档被清 | **Hyrum 型**：改共享件，破坏了消费者依赖的、从没被写下来的性质 | ❌ 无 |
| 2 | commit 写「不是两份拷贝，是同一份」，实际还有第三份 | 全称断言未做机械校验 | ⚠️ 有机制（AST 普查测试）无触发规则 |
| 3 | 加了个能力接口解计数泄漏，事后发现规范定了 MUST、两个官方实现是另一形状 | 设计前没读规范/现成解法 | ✅ 已有两条规则，**没被执行** |
| 4 | 复用一个表示「有没有 taskID」的 bool 去判「认不认识这个请求类型」⟹ 每次新建会话打 ERROR | **借来的量**：X 的名字里没有 Y 的意思 | ✅ 已有规则 + 判别式，**没被执行** |
| 5 | 在既有 godoc 与其声明之间插新声明、没留空行 ⟹ 整块改嫁，原符号零文档 | Go 注释归属规则的词法意外，**无契约参与** | ⚠️ checklist 有一条「当场 go doc 看一眼」，靠自觉 |
| 6 | 给 conformance 写的自检重抄了被测逻辑，从不调用真断言 | 同 #2 | ⚠️ 同上 |
| 7 | 给函数加提前返回，没把已累积的待清理资源带出那条路 ⟹ 资源孤儿 | 控制流出口路径不完备 | ❌ 无 |

**关键纠正**：#1 是唯一的「生产者破坏下游」；#4 方向相反（消费者误读上游）、#5 无契约参与、
#7 是函数内部控制流。**合并成一个「插入」形状会让 #4 逃过「借来的量」那节已经写对的判别式。**

#3、#4 的共同点更值得记：**它们是已有规则没被执行，不是缺规则。加规则不会修好它们。**

## 二、这个现象在文献里的名字（核实结果）

| 概念 | 核实 | 刻画了哪几条 |
|---|---|---|
| **Yin et al., "How do fixes become bugs?"（FSE 2011）** | ✅ 真实，最贴的量化基线：多个操作系统里 **14.8%–24.4%** 的 post-release 修复本身是错的且影响到终端用户；**并发 bug 的修复错误率 39%** | 整体基线 |
| **Hyrum's Law** | ✅ 原文：足够多的使用者之下，契约里承诺什么都不重要，**所有可观察行为都会被某人依赖** | **只刻画 #1** |
| **SZZ** | ⚠️ **不是这个现象的名字**，是从版本历史里挖「引入缺陷的 commit」的算法；且自身精度存疑（被判定为修复的 commit 约一半不是；约 20% 被追溯的行其实是重构） | 不刻画任何一条，别当术语用 |
| 契约 widening/narrowing、LSP、前后置条件 | ⚠️ 能描述 #1，**但要求那条性质先被写下来**——而 #1 的性质从没被写下来。用契约语言描述会漏掉实质 | 听着像，不是 |
| change impact analysis / ripple effect | ✅ 真实分支，但它是**分析技术**不是失败模式的名字 | 是 #1 的对策类别 |
| feature interaction problem | ⚠️ 讲两个各自正确的特性组合后出错 | 七条里没有一条是这个 |

## 三、可机械化的部分（按证据强度排）

### 3.1 godoc 吞并（#5）——能做 gate，我原本的信噪比估计是错的

我自己写过一个检测器，判据是「doc 第一句讲的符号 ≠ 声明的符号」，三轮收窄仍有 **242 条噪声**，
判断「做不成 gate」。**判据用错了**：那需要识别「一句话在讲谁」，于是每条以别的符号开头的
正常注释都命中。

成熟工具用的是**纯位置谓词**：`strings.HasPrefix(docText, Name+" ")`——不试图理解注释在讲谁，
只要求约定。本仓实测：

```
staticcheck -checks="ST1020,ST1021,ST1022" ./...
→ 11 条
分母（go/ast 独立数，口径 = 排除 example/ 与 redis/ sql/ a2a-zk 三个独立 module）：
   929 个导出函数/方法，其中 812 个有 doc
```

⚠️ 分母的口径必须写出来，不然对不上。调研报告给的 917 / 852 是**另一个口径**（含
`example/`），独立审计在父树上精确复现了它；我上面那组 929 / 812 排除了 `example/` 与三个
独立 module。**两个都对，只是数的不是同一个集合。** 我一度把这写成「对方的数不可复现」，
那是错的——记一笔：**两次测量不一致时先问口径，别先假定对方错。**

**噪声不是 242，是 11**，其中 3 条是固定假阳（`schema/message.go` 的 `type (...)` 块里分节标题
被当成下一个 spec 的 doc）。

⚠️ **这个低噪声依赖本仓已有的「符号名 + 中文」godoc 约定**（99.5% 已合规）。换个不写符号名
开头的仓库会炸。

**当场揪出主干 4 处未修实例**（不是「一年两次」）：

| 位置 | 症状 |
|---|---|
| `agent_v2/approval.go` | `WithApprovalHeuristic` **零文档**，它讲安全 seam 的正文挂在 `ApprovalScope` 上 |
| `agent_v2/config.go` | `WithToolFilter` 只剩一句断尾，语义正文挂在 `WithToolMiddleware` 上 |
| `compose_v2/graph_loop.go` | `type RunOption` 挂着 `Run` 整段「核心不变量」，`RunOption` 自己零文档。⚠️ 我起初以为那是正本的**逐字副本**且「比正本旧」——**两条都假**：它比正本多两句（ctx 检查时机、ApplyAll 的超步内并发安全性），是**严格更全**的那份。已并回正本 |
| `compose_v2/serialization.go` | `CheckpointSchemaVer` 挂着 changelog 尾巴。~~未修~~ **已修（2026-09-23）**：补回 v13，changelog 并成一段、与常量 doc 之间空行（原文：没有声明因此丢文档，只是常量 doc 前挂了段噪声 + changelog 断成两截；顺带那张表缺 v13） |

**它抓不到的一半**：位置谓词的早退是「没有 doc 就返回」——**受害者侧（符号变成零文档）它不看**。
插入的新声明若自带以自己名字开头的 doc、又紧贴旧 doc，合并块首词就是新声明的名字，检查静默
放过而旧符号照样零文档。补这个洞要的是**差分**：「HEAD~1 里有 doc 的导出符号，现在没有了」。

### 3.2 「只有一份实现」（#2）——本仓已有正解，别引新工具

`agent_v2/member_dispatch_accounting_test.go` 的 AST 普查 + 按 (文件, 函数) 计次白名单，编码的是
**意图**（「只有这 N 处可以做 X」）而不是从 token 相似度猜。缺的不是机制，是**触发规则**：
commit message 里出现「只有一份 / 唯一 / 都走 / 已收敛」这类全称断言时，必须同时有一个这样的
普查测试。

补充信号 `dupl`（token-based 克隆检测）实测：默认阈值 150 下 **4 条全真、0 假阳**，阈值降到 50
崩掉（50 条）。默认阈值找到两处**尚未收敛**的重复：

- `LoopAgent.Run` ≡ `ReflectAgent.Run`：各 67 个有效行（去注释空行），其中 **55 行逐字相同**
  （82%），最长连续相同块 18 行
- `ParallelAgent.Run` ≡ `RoutingAgent.Run`：66 / 69 有效行，**54 行相同**，最长连续块 18 行

⚠️ 这两组数字**是我自己重量的**。调研报告说的是「188 行 / 150 行逐字重复」——那是克隆检测
工具报的**行号跨度**（含注释和空行），不是重复的代码行数。重复是真的（82%），量级被放大了
约 3 倍。**又一次：抄来的数字进文档之前必须自己复现。**

局限：只找**语法**克隆。短于阈值（约 15–25 行）或写法不同的语义重复必漏——所以它是补充信号
不是 gate。顺带：本仓那套 typed-nil 守卫按名字 grep 找不全（**8 个包、7 个名字**），克隆检测
反而找得到。

### 3.3 自检不调真断言（#6）——覆盖率归属，比变异测试便宜几个数量级

规则形态：**一个声称守护 X 的测试，单独跑时必须对 X 产生非零覆盖**。

```
go test -run TestSelfCheck -coverpkg=./pkg -coverprofile=cov.out ./pkg   # 通过
go tool cover -func=cov.out
  pkg.go: AssertOrdered   0.0%      ← 自检从没调过真断言
```

**0% 无歧义，构造上无假阳。** 变异测试（`gremlins` / `ooze` / `go-mutesting` 系）也能抓，但慢
几个数量级且要引新工具。

### 3.4 Hyrum 型（#1）——golden fixture 冻住可观察行为

Go 官方的 API 兼容工具**明确答做不到**：`apidiff` 的 README 自己写着「任何兼容性检查工具只能给
出近似，**没有工具能检测行为变化**」。它只做类型层面对应，判据是「客户端代码会不会编译不过」
——七条链里签名一个都没变，零命中。**这条路是死的。**

真正在用的机制是把可观察行为**冻进 golden fixture**：把每个类型在每个版本序列化存进
`testdata/vX.Y.Z/`，用旧 fixture 跑当前代码。关键约束是「给既有类型加字段**不应**需要改这些
fixture」——即 **fixture 变了就是行为变了**，改它需要在 commit message 里贴 diff 并接受严格评审
（用显式环境变量制造摩擦，防止被顺手 regenerate 掉）。

成立前提：那条性质**能被序列化成字节**。#1 能——「一次 Run 产生的挂起清单」是可序列化的。
其余六条不适用。

⚠️ **这一条是本报告里唯一没有在本仓实测过的方案**（只核实了机制本身）。

### 3.5 不适用的：契约测试（Pact 一支）

它是**跨进程**的（消费者录期望、提供者回放）。已知批评：事实源分裂（OpenAPI + pact JSON 双维护）、
HTTP 之外支持弱。**库内没有等价物**——库内消费者和提供者在同一次编译里，那个位置上的等价物就是
本仓已有的 conformance 套（`store/conformance` / `checkpointer_conformance` / `history_conformance` /
`a2a/registry/conformance` / `a2a/server/taskstore_conformance`）。方向对，问题在 §3.3。

## 四、流程层面（核实：区分「有制度」和「制度针对这个问题」）

| 机制 | 针对这个问题吗 |
|---|---|
| **Beyoncé Rule**（"If you liked it, you should have put a CI test on it"）| ✅ **唯一直接针对的**。它是 Hyrum's Law 的配套制度：既然隐式依赖必然存在，就把举证责任推给依赖方。**代价是它分配责任而不解决问题**——对「生产者和消费者是同一个人」的场景分配无意义，但推论有用：**想保住的每条隐式性质，必须当场写成测试**。#1 正是没写 |
| 大型项目的 API review 流程 | ⚠️ 有成文 checklist，但目标是**外部 API 形状的长期稳定**，不是「改共享函数会碰坏哪些调用方」。别照搬 |
| OWNERS 式强制评审人路由 | ⚠️ 价值在「改共享件时强制把消费者方的人拉进来」。单人仓路由到自己等于没有 |
| RFC 的 drawbacks / alternatives 段 | ⚠️ 逼作者写下「考虑过哪些替代」，对 **#3** 有效，对其余无效 |

**没有找到任何项目有「改共享代码时必须列出所有调用方」的成文 checklist。** 大型项目一律用
**机械手段**而非人肉列举——因为人肉列举在本仓已被证伪四次（typed-nil 守卫 6 vs 8、协议扩签
「3 worker 都改」实改 1、`5afb8eb` 漏 2 处、dispatch 计数）。

## 五、结论

**本该被机械拦住的 4 条**：#5（位置谓词 + 差分谓词）、#6（覆盖率归属）、#2（AST 普查 + 触发规则）、
#1（golden fixture）。

**只能靠纪律、不硬造工具的 2 条**：
- **#4**（借来的量）：没有工具能判断「这个变量的名字里有没有那个意思」。本仓已有规则和判别式，
  **该做的是把它加成那张表的新一行**，不是发明新形状。配套要求已经写着：**每个借用点必须有一个
  N=2 的用例**。
- **#7**（提前返回丢累积资源）：现成 linter 只有按资源类型写死的那几个，没有通用的。**正解是
  结构性的不是检查性的**——把累积量改成具名返回值 + `defer` 收尾，让「新加一条 return 就漏掉它」
  在语法上不可能。这不是 lint，是设计。

**#3 既不属于机械也不属于新纪律**——两条已有规则没被执行，加规则不会修好它。
