## 1. 位 1+2：成员记忆写不进去 + 共享 ns 键逐字撞

**对端**：两家在此位都是「框架不自动写」——LangGraph 框架零自动写 store（namespace/key
100% 业务选，仅语法校验；平台租户前缀是 opt-in Auth handler 改写）；eino 长期 store 自动写
特性缺席（最近似物 `OutputKey` 写 per-Run 共享 Values，同 key 后写覆盖靠约定，损害被
per-Run 生命周期封顶）。**两家的残留失败模式恰是我们实测的**：同 (ns,key) upsert 静默覆盖
零告警、复用子图多实例业务忘带身份互覆。

**判决：原拟修法成立且能做到比两家强。** 我们有自动写（`WithStoreMemory` 是自家 feature），
不能靠特性缺席免疫，必须补身份维——而两个前提**已存在不用新造**：

- 写入点（`agent_v2/basic_agent.go:1486` commitFinal）ctx 里已有写入者位置——`runMember`
  push 的历史 slot（`agent_v2/history_slot.go:102`）；
- 装配期撞车检测已有——注册名 `AddBranch`/`AddStep` 重名当场 panic
  （`agent_v2/parallel_agent.go:181`、`agent_v2/sequential_agent.go:140`）。

删开关的合法性：`WithStoreMemory` 本就是 per-agent 配置，成员写不写该由成员自己的配置
决定——开关（`IsSubAgentStoreScope`）是框架越俎代庖；身份维进 key 后 ISSUE-84 担心的
「双重持久化」退化成「各写各的」，正是想要的语义。

**代价**：slot 改名孤儿化旧 key（历史层同款、已文档化的代价）。缓解：允许业务在
`StoreMemoryConfig` 显式给稳定 writer id，缺省用 slot。

**效果对比**：根治（类型 2 默认消失、键结构上不撞）；两家把身份维推给业务，我们框架
自动写就框架自动带身份——**超两家**。

## 2. 位 3：持久转交跨租户串台

> ⚠️ **2026-08-20 修正：本节上一版的结论「持久转交改 opt-in 缺省关」判错，已撤销。**
> 错因是把问题框成「怎么消除串台」，于是答案自然长成「关掉功能」——而该问的是
> 「怎么在**保住 handoff 语义**的前提下消除串台」。这正是 CLAUDE.md「派调研之前先问
> 一句我是不是已经默认了某个前提」那条规约的又一次实证。

**先把三个层次拆开**（混在一起谈是上一版判错的直接原因）：

| 层次 | 我们 | LangGraph | eino |
|---|---|---|---|
| **一次 Run 内，转交后归谁** | B | B | B |
| **下一条用户消息还归不归 B** | **取决于业务有没有声明会话 ID**（见下） | **归 B**（active_agent 是 state 字段随 thread 存档） [二手] | **不归**（每次 `Run` 从构造期根 `r.a` 进 + `ctxWithNewTypedRunCtx` 新建；`TurnLoop` 的 `PrepareAgent` 是 **Required** 回调、每轮由业务给谁跑；`lastAgent/activeAgent` 类字段全仓零命中） |
| **归属（谁能碰这个会话）** | 无 | **平台层 Auth**（引擎层 thread_id 也是裸字符串，同样无租户） | 无（无服务层） |

**第一层三家一致**——「转交之后归当前接手方管」是 handoff 的定义，不是争议点。
**第二层 LangGraph 与我们同侧**（持久归 B），eino 是另一侧。所以「默认关」等于把语义从
LangGraph 侧切到 eino 侧，**那不是修 bug，是换产品语义**——handoff 少了跨轮延续就退化成
每轮重选的 Routing。

**新查明的事实（推翻「要改成 opt-in」这个前提）**：持久**已经是条件性的**——
`handoffThreadID`（`agent_v2/handoff_agent.go`）取 `compose_v2.GetThreadID(ctx)`，
**取不到就回落 `session.RunID`**；而 RunID 每个任务新铸 ⟹ 没声明会话 ID 时，
下一个任务根本读不到上一个任务的 active。所以：

- 纯库内用法（不声明 ThreadID）：**本来就不持久**，无串台面；
- a2a / agui 用法（wire 的 ContextID / threadId 自动成为 ThreadID）：持久生效——
  **而这恰好就是唯一会串台的场景，也恰好是该管归属的那一层**。

**判决：本位没有独立修法，它是位 4 的下游。** 位 4 的边界 authorize seam 一旦到位
（「这个 principal 能不能碰这个 threadID」），不同租户拿不到同一个 threadID 的访问权，
串台自动消失——**这与 LangGraph 的结构完全同构**：它引擎层同样不管归属（thread_id 裸
字符串），归属在平台层 Auth 用 owner metadata + filter 解决。我们把它放在 a2a/agui 适配层，
位置对应关系一致。

**本位剩下的动作只有两个**（都不改语义）：

1. 边界 seam 落地后，把认证主体注入 `handoffActiveNS` 的归属段（跟着位 4 一起做）；
2. 未配 seam 时是单租户信任域——写进「已知限制」（LangGraph 同档，且它默认 fail-open）。

## 3. 位 4：wire 会话 ID 单独构成完全控制权（原题「挂起会话可被任意 threadId 销毁」）

> ⚠️ **2026-08-20 二次修正：本节的「默认 reject」改版同样判错，已撤销。**
> 这是**同一个错误模式的第二次**（第一次是位 3，见 §2）——判别式补在 §3.1。

**先纠正现象描述**（上一版把攻击面写成了并发误伤）：入口按 `len(in.Resume) > 0` 分流
（`agui/handler.go:197`）——

- 用户**回答**中断 → 前端带 `resume` 字段 → 走 `serveResume` → **根本不碰清理路径**；
- 用户**不回答、改问别的** → 无 resume 字段 → 走 `serveRun` → 命中 `handler.go:220` 清挂起 cp。

**所以正常单客户端流程下不存在误伤**：220 行处理的是「用户放弃旧中断、问新问题」，
那个场景下清掉挂起 cp **是正确行为**（否则孤儿 cp 泄漏）。已有的 busy 保护
（`handler.go:216`）另管「两个请求同时在跑」。

**真问题是归属，不是并发**：实测结论应表述为「wire 来的会话 ID **单独构成完全控制权**
——持有它即可销毁挂起会话、续跑他人会话，框架没有任何地方能问『这个 ID 是不是你的』」。
（原实测记的「不需要 interruptId」也误导：run 路径是新一轮运行，本来就不该要 interruptId。）

**两版修法为什么都不成立**：

| 版本 | 为什么不行 |
|---|---|
| 原版：活对象引用当凭证 | HTTP 客户端手上只有字符串，对象引用传不过来，落不了地 |
| 改版：挂起时新 run **默认 reject** | ① 破坏「用户改主意问别的」这个常见正常场景（前端得显式带参数才能问新问题）；② **治不了真问题**——第三方拿到 ID 后同样能带那个显式参数来顶。**对合法用户是负担，对攻击者是零障碍，安全上纯负收益** |

**判决：本位只加 authorize seam（principal × threadID × action），不改任何默认行为。**
理由与位 3 同一条：threadID 由 wire 给，「谁能碰它」只有边界层答得上——引擎层拿到的是
裸字符串、手上没有可用判据。**位 3 与位 4 就此合并成一条：wire 会话 ID 的归属维。**

**次要项（不改语义，可选）**：顶掉挂起会话现在是静默 `dropCP`，可加一条事件/日志让业务
能发现异常模式（同一 ID 被反复顶）。不阻塞主修法。

### 3.1 判别式：攻击面 ≠ 功能 bug（两次踩同一个坑之后补的）

位 3 和位 4 我都把**攻击面**当成**功能 bug** 来修，于是修法都长成了「限制正常功能」：

| | 真问题 | 我给的修法 | 后果 |
|---|---|---|---|
| 位 3 | 不同租户撞同一会话 ID | 持久转交默认关 | 砍掉 handoff 跨轮延续语义 |
| 位 4 | 第三方持 ID 即可销毁 | 挂起时新 run 默认拒 | 破坏正常场景，且挡不住攻击 |

> **判别式：先问「这件坏事发生时，是谁在做」。**
> 合法主体的正常操作被误伤 ⟹ 功能 bug，修功能；
> **非法主体冒充合法主体 ⟹ 归属问题，修归属（认证/授权），不动功能。**
> 用限制功能去堵冒充，通常两头落空——合法用户被挡，冒充者照样能满足那个限制。

## 4. 位 5：annotation 通道未授予方可用

**对端**：eino 是此位最强参照——信号一律 typed Action 挂事件流，**消息/metadata 零触发
路径**（结构上不可能），RunPath 框架盖章（非导出字段）+ agent-tool 边界剥离；域内
`SendToolGenAction` 开放 by design 无白名单。LangGraph 单载体 Command（annotation 第二通道
特性缺席）但**来源不设防**：任何节点一行 `return Command(goto=...)` 就改流向、无授予概念，
`goto` 打错还**静默丢弃**（warning 日志 + no-op）；prebuilt 路由读消息内容，伪造一条带
tool_calls 的 AIMessage 就能间接驱动含 handoff 在内的任意已注册工具。

**判决：原拟修法成立，可根治，修完效果 ≥ eino > LangGraph。** 修后信号唯一载体=槽
（框架私有类型），唯一写入口=transfer 工具（grant 门控 + 候选校验 + 非法目标**可见**软失败
回灌）——比 eino 多一层 grant 门控（它域内任意 tool 能发）、比 LangGraph 多授予概念和可见
失败。

**需要补的一件**：程序化成员（非 LLM 的自定义 Agent）的合法转交出口——现在 annotation 是
它们唯一的路，删掉必须给 typed 替代。机制现成：grant 本来就经 RunOption 进成员签名
（`handoff_agent.go:559-560`），自定义 Agent 实现从自己的 Run opts 里取 grant 行使即可，
补一个公开 helper 的事。

**范围界定（2026-08-20 复核，改变了原第三问的性质）**：两个模型的 annotation **不是同一条
通道，风险差一个数量级**——

- **模型 B 的 `out.Annotations` 读取**（`handoff_agent.go:591-596`）：读的是 **sub-agent 的
  产出消息**，任何能改产出的代码（业务壳、包装 agent）都能写 ⟹ **这才是那条伪造通道**，
  且它绕过 grant（tool 路径有 grant 门控，annotation 路径只校验候选名合法）。要删的是它。
- **模型 A 的 `HandoffSignalKey` 协议**（`handoff_builder.go:47,222`）：**唯一生产使用者是
  HandoffAgent 自己**（`handoff_agent.go:495`，`HandoffAgentBuilder` 不是对业务开放的原语），
  写入者是框架自己的 stepFn（`handoff_agent.go:610-614` 写回），读取者是模型 A 的条件边，
  **中间不经业务**。它是框架内部两点间的传值，删它需要另造 channel、收益低。

**残留观察（非本次范围）**：模型 A 的载体是**消息字段**，而消息会流向历史层/压缩层——
两家都不用消息字段承载控制信号（LangGraph 引擎对 `additional_kwargs` **零读取**，路由目标
住 state channel；eino 是 typed Action 挂事件，合成消息「纯为历史可读性」）。框架已有
`clearHandoffTargetAnnotation`（`handoff_builder.go:296`）在清，说明这个残留是已知的。
换 channel 载体可作为后续清理项，不阻塞位 5。

## 5. 位 6：转交信号跨存档靠工具体重跑 + 豁免名单

**对端在此位收敛到同一句话：控制信号进持久化载体，名单就没有存在理由。**

- LangGraph 是六位里唯一的**纯结构解**：handoff Command 早被翻成普通 channel 写，成功
  task 的写入**即时单独落盘**（`_runner.py:604-613` `put_writes`），「GraphInterrupts are
  not considered failures」不掐兄弟（`_runner.py:622`），resume 回放已落盘写入、只重跑
  没有 writes 的 task（`main.py:2968`）；v2 档每个 tool_call 独立 Send task。
  **豁免名单特性缺席**——豁免单位是 task，判据是「有没有已 commit 的写入」，一律适用。
- eino：信号住 **checkpoint 化的 State**（`ToolGenActions` + `ReturnDirectlyEvent`），
  工具重放是通用的按 callID `ExecutedTools` 记账（`compose/tool_node.go:806-818`），
  **无名单**——原文结论「transfer 不需要豁免，因为它的副作用（Action）本身进了 State」。
  它的残留坑：自定义非 return-direct action 在兄弟中断时**静默丢**（事件已消费、回放不过
  middleware）。

### 5.1 场景真实性实测（2026-08-20，真 LLM）

上一版的场景（transfer 成功 + 兄弟工具中断 → 存档 → 信号要活下来）此前**只在 mock 里
构造过**——让假模型同时返回两个 tool_call。真实 LLM 会不会这么调，从没量过；不量就修，
等于拿自己造的场景当需求。实测程序 `example/scenarios/transfer_batch_probe`（3 档诱导
× 3 次，`OnModelEnd` 抓每轮 tool_call 名单）：

| 场景 | prompt 取向 | 结果 |
|---|---|---|
| A | 中性（「账单金额好像不对」） | **3/3 分两批**：先 `query_order`，再 `transfer_to_agent` |
| B | 暗示先后（「查一下…然后转给专员」） | **3/3 分两批** |
| C | 强诱导（「同时做两件事…不分先后」） | **3/3 同批**（`query_order, transfer_to_agent`） |

**结论：场景真实，但不是自然常态。** 自然语境下模型自己会分两轮（先拿信息、再决定转交），
只有用户明确要求「同时做」才同批 —— 15 个批次里 9 个含 transfer、其中 3 个同批。
⟹ **位 6 的修法需要做**（不能靠「这场景不会发生」免掉），但优先级不必按「每次转交都踩」算。

**副产物（另一个问题，已单独记 backlog）**：对比两组 final —— B 组（分两批）答得出
「金额 ¥238.00」，C 组（同批）只答得出「状态查询已完成」**说不出金额**。因为同批时
`query_order` 的 tool_result **不会回给 front 的 LLM**（`basic_builder.go:630`：任一
return-direct 就短路），副作用真的发生了、产出却没人看得见。这是「return-direct 与别的
工具同批」这个组合本身的语义问题，与位 6 的信号存活正交。

**判决：原拟修法（删名单 + started 事实交模型）不成立——错配了子问题。** 那个形态解的是
「会话修复时发现结局未知的悬空调用」（工具结果没落盘、无从判断执行没执行），而我们实测的
问题是「信号载体不进 cp、靠重跑续命」。硬套的结果是把一个**框架有能力结构化解决**的问题
降级成「让模型猜」。「合成 error + 告知模型」保留为**另一个位置**的补强（真正
outcome-unknown 的场景，如 durability async 硬崩后的悬空调用），不再当本位主修法。

**修正后修法（对齐两家的结构解，落在我们已有的底子上）**：

1. transfer 工具把 target 写进 `tool.Result.Metadata`（typed 声明；现在只以散文
   「已转交给 %s。」留在 tool_result 文本里，`agent_v2/handoff_tool.go:259`）；
2. **memo 记账已是 LangGraph 档**——`toolCallMemo` 每成功一个就存、随 `cp.NodeStates`
   持久，键 `(tc.ID, 批内下标, 工具名)` 比 eino 的 `ExecutedTools[callID]` 还多两维
   （`basic_agent.go:2140-2165`）；缺的只是「控制效果声明 + 重放」协议：resume 命中 memo
   时，从记录的 Metadata **重放 `slot.put`**——契约从「重放产出、不重放副作用」扩成
   「重放产出 + 重放**声明过的**控制效果」；
3. transfer 随即从 `isFrameworkTool` 豁免名单里出来；名单判据从「名字在表里」变成
   「Result.Metadata 有没有声明」——**工具自述（出路④），业务自定义控制流工具走同一
   协议**，名单可趋零（`tool_search` 揭示集同款处理）。声明协议对业务开放正好避开 eino
   的残留坑（它的自定义 action 无此协议才静默丢）。
4. 伪造面不复活：重放读的是 memo（框架私有、业务够不着），不扫消息——与位 5 的删
   annotation 不矛盾。

**效果对比**：信号结构化存活=两家档；名单消亡机制=两家档且对业务工具开放一档更完整；
记账粒度（tool_call 级 + 三维键）不输任何一家。**根治。**

## 6. 下标裁决跨批冲突

对端实证：LangGraph 的 idx 是**提交点铸的全局确定性下标**（写入合并排序后编号，并发分支
不可能同号）＝出路②。我们的槽形态里组合成员对 HandoffAgent 不透明，跨批全序要动的面大；
而拒绝已证良定义（root-causes §1.4 复查）。**推荐**：put 记冲突（加维保证据）+ take 见
冲突**软失败回灌模型**（复用 `HandoffTargetInvalidErrCode` 范式，「两个分支同时要求转交，
请裁决」）——即「拒绝 + 交还模型」的混合，实现小、失败可见；提交点全序留作后续可选。
