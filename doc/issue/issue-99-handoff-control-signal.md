## 0. 一句话根因

**我们把控制信号放在业务能寻址的容器里**：

| 信号 | 容器 | 业务够得着吗 |
|---|---|---|
| 「这场对话现在归谁」（持久 active） | 业务提供的 `store.Store`，key = `("__handoff_active__", 编排名, threadID)` | **能**——那个实例是业务 `new` 的 |
| 转交目标（本次调用） | ctx 上一个 per-attempt 新建的可变槽 | **能**——ctx 是环境 |
| 转交目标（兜底） | 最终消息的 annotation | **能**——任何改得到最终消息的东西都能写 |

三条是同一个形状的三个实例。

## 1. 待决项

### 决定 1 — 能力授予的形态

现状：能力做成一个值，沿 `RunOption` 一层层显式传（9 个转授点 + 7 个自查点），
外加一套受让方身份判定（穿透 Go 匿名嵌入 / 避开 interface `==` 在不可比较类型上 panic / 限深防环）。

**这套成本的来源**：能力要穿过一段**我们不控制的传递路径**——`RunOption` 可被任意转发，
于是每个消费者必须验「这份是不是发给我的」。

**实测事实**：我们支持「候选是一棵树，能力到叶子」（对照组候选=BasicAgent、实验组候选=Sequential
包着同一个 leaf，两组 `leaf=1 billing=1` 一致）。

| 选项 | 会引出的新问题 |
|---|---|
| **A 保持现状** | 无新增；代价是那套身份判定持续存在（现有机械对账盯着） |
| **B 候选限为单 agent** | **守卫做不出来**：`Agent` 是 4 方法开放接口，业务自写的组合编排跟 BasicAgent 类型上**不可区分**。类型断言列举框架自带的 7 种 ⟹ 漏掉业务组合 ⟹ **注册成功、叶子静默拿不到能力** |
| **C 保留树候选、只有根层能转交 + 报错** | 同上（报错也要先判出「这是棵树」）；外加**能力回退**（今天叶子实测能转交） |

**倾向 A**——不是因为它好，是因为 B/C 的守卫立不住，而没有守卫的 B/C 比现状更糟。

### 决定 2 — 成员的 `WithStoreMemory` 写不进去

**已复现**：同一个 BasicAgent，顶层跑 → store 里 1 条；当 Sequential 的一步 → **0 条**，`err` 全程 nil。

成因：`runMember` 无条件 push `WithSubAgentStoreScope(true)`，而这个 flag 全包只有一个消费者
——`BasicAgent.commitFinal` 据它跳过 `store.Put`。它的模型是「让顶层 BasicAgent 唯一写入」，
父是 BasicAgent 时（`AgentAsTool`）成立，**父是编排时没有人写**。

pre-existing（收敛前 9 处逐字相同），现已收敛成一行 ⟹ 一个决策点而非九个。

| 选项 | 新问题 |
|---|---|
| 保持 | 无新增；业务配了不生效**仍然静默** |
| 按父类型分档 | `runMember` **判不出调用者是谁**；要判就得调用点传 flag ⟹ **又是一条 per-dispatch 协议**，正是这轮刚消灭的那类东西 |
| 给业务开关 | 默认值选哪个都改一部分现有行为 |

**倾向：保持行为 + 把「配了不生效」变响**（成员配了 `WithStoreMemory` 且 scope=true 时 warn 一次）。

### 决定 3 — 转交信号的载体

> ✅ **已决（2026-10-08）**：转交与路由都改成**跟着写入者的提交走的上行信号**（`compose_v2/signal.go` +
> `agent_v2/side_signal.go`）。下文担心的「channel 是单个图的 state、信号要跨到上层的图」由引擎在图成功
> 跑完时把已提交的信号交给调用它的那段执行解决——不经 `AgentEvent`，也不让业务能写（收件人由引擎铸、
> 带随存档走的密钥，手写信号 JSON 冒充不了）；一个收件人上是单值格子：先后做出的后者为准，并发做出的在
> 合并点比对、不一致报错（不可重试、不清档）；消费方在那次调用成功之后取。决策与对照见
> [handoff-control-signal.md §8](../description/three-way-comparison/handoff-control-signal.md)。
> **2026-10-09 改**：同一超步的成员「不一致才报、不清档」已推翻——只能有一个成员做决定（值相同也算），
> 冲突带 `ErrRunAborted` 终局，`ParallelAgent` 的分支不再拿转交 / 路由能力；业务经 `JoinSignals` 合并的
> 几路仍是不一致才报，但同样终局（推翻的只是「不清档」）。见上述文档的 2026-10-09 行。

**根因（两条 backlog 合并成一条）**：

> **裁决域和载体域错配。** 裁决判据是「本轮 tool_call 下标」（作用域 = **一次 LLM 调用**），
> 载体是「一次 Run 调用的 ctx 槽」（作用域 = **整棵编排树**）。两域不同 ⟹ ParallelAgent
> 两个分支的 idx 都是 0，落进同一个槽，谁赢取决于哪个 goroutine 先写。

同一个根因也解释了第二条：**我把一个「决定」存成了「运行时副作用」**。决定不是持久数据、
也不是持久数据的纯函数 ⟹ 续跑时必须靠工具体重跑来重新产生 ⟹ 转交工具必须豁免工具结果备忘
⟹ **续跑时必然重放副作用，跟备忘存在的理由直接对冲**。

**正解形状**：把**裁决**与**传值**拆成两件事。

- 裁决：工具跑之前、从有序 tool_call 列表算出的标量 ⟹ 跟 goroutine 完成顺序无关
- 传值：挂在这一层 agent 自己的持久态上（每个 sub-agent 一份）⟹ 两个分支天然两份，且随存档走

两条 backlog 会一起消失，备忘豁免也解掉。

**新问题（必须先解决再动手）**：

- **「传值挪到 channel」在我们这儿走不通**：channel 是单个图的 state，而转交信号要从 BasicAgent
  的图**跨到** HandoffAgent 的图。我们的跨层载体是 `AgentEvent`。
- **而「给 AgentAction 加转交字段」正是本轮早期被否决的方案**（否决理由：洞从仓内 0 处形状搬到
  4 处形状，新增伪造/重放，Parallel/Plan 静默丢）。
- **但当时否决的不是同一个东西**：当时的形态是「stepFn 扫最终消息的 tool_call」——**裁决和传值
  仍然混在一起，只是换了容器**。裁决前移之后是另一个形态。**不能直接复用当时的否决，要重新评估。**

### 决定 4 — 持久 active 的存储位置（H2）

「跨 Run 持久」+「业务够不到」这两个要求，在**「业务提供持久化后端」**这个前提下矛盾：

- 进 cp？cp 是单次 Run 临时态、成功即清，跨不了 Run
- 进 HistoryStore？append-only 的会话历史，语义不对
- 框架自持一个？跨进程/重启就丢，违背「持久转交」的初衷
- 要业务给两个 store？业务照样持有框架那个的句柄

**倾向记成「非目标」**：除非改掉「业务提供通用 KV 存储」这个前提（把 `store.Store` 从通用 KV
收窄），否则无解。收窄是另一个量级的改动。

## 5. 二轮调研的修订与新发现（2026-08-19 第二轮）

四条待决全部做了第二轮，逐条挑刺。**修订三条、新增一条真 finding。**

### 5.1 【推翻】「跨 Run 持久转交是我们独有的」

**不是。** MAF .NET 有逐字同款：`HandoffWorkflowBuilder.EnableReturnToPrevious()`，状态
存 workflow shared scope（key/scope 都是**裸字符串，连 `_` 前缀都没有**）、进 checkpoint、
跨进程存活；业务经**公开** API 就能改，且它的 scope 比较**完全忽略 executorId**。
**它的位置跟我们完全一样，标记还比我们弱**（我们至少有 `__` 前缀 + 候选白名单校验）。

⚠️ **但它默认关**（`_returnToPrevious = false`），开关**以行为命名**（`EnableReturnToPrevious`
说的是行为不是机制）。我们现在是无条件读写，业务**连「我不要」都表达不了**。

### 5.2 【推翻】「四条路都走不通」

| 路 | 判定 | 依据 |
|---|---|---|
| 挪进 cp | **技术上通，但零安全收益** | 「cp 成功即清」是我们自己定的生命周期不是 cp 的本性（LangGraph 的 cp 是 thread 级、永不自动删）。但 `GetCheckpointer(ctx)` 是公开的、业务本来就持有 ⟹ 换了个业务同样拥有的容器 |
| 挪进会话历史 | **半通，买到「可见性」** | append-only 完全能表达「当前」；代价是读路径 O(1)→扫历史，且归属是编排结构的函数（CLAUDE.md 已记它的脆弱性） |
| 框架自持 store | **真死路** | 五家零先例；跨进程重启就丢 |
| **要求两个后端** | **走得通，先例最强，而且我们已经在这条路上** | LangGraph `compile(checkpointer=, store=, cache=)` 三后端职责分离，且**节点面前只有 store**（`Runtime` 上没有 checkpointer）。它买到的不是「业务够不到」，是**职责分离 + 调用方手边 API 收窄** |

**所以问题问错了**：四条路都在答「怎么让业务够不到」，而五家在**库层**无一回答这个问题。

**根因的精确表述**（比「控制态放哪」准）：缺的是**「封闭词汇表 × 跨 Run 生命周期」这个组合**——
我们的 Channel 词汇表封闭（`ChannelWrite` 是密封接口、未注册 channel 直接报错）但生命周期是
单次 Run；`store.Store` 生命周期跨 Run 但词汇表开放。LangGraph 的 channel_values **两个都有**。

### 5.3 【订正】handoff active 缺归属协议 —— 原记「跨租户串台」，框架和定级都不对

> ⚠️ 本节的**第一版记错了两处**，独立审计逐条打回。保留订正过程是因为错的那两处
> 正是最容易再犯的：**fixture 过度指定**（让缺陷显得比实际稀有）和**定级用了个
> 框架从未被给予判别手段的说法**。

**机械事实为真**（独立审计复现，输出逐字一致）。但：

1. **原 fixture 过度指定**。我写的前提是「两租户共用一个 store 实例」；实测**零 store
   配置**就能发生——`storeForActive` 落到 `h.defaultStore`（lazy init 的 InMemoryStore），
   而单例 agent 是库的普通用法。这条前提让缺陷显得比实际**稀有**。
2. **「跨租户串台」这个说法不成立**。实测「A 的第二轮」与「B 的第一轮」在框架侧
   **计次与最终文本完全相同**——`readPersistedActive` 的全部输入只有 (store 视图,
   编排名, threadID)，三者全等时它们**就是同一个输入**。而 threadID 是本框架里声明
   会话身份的**唯一**入口，两个调用方递同一个值，就是在按协议声明「这是同一场对话」。
   把它叫「串台」是**把一个框架从未被给予判别手段的场景说成判别失败**。
3. **定级错了**。泄漏的是**一个字符串**，且必是 app 自己注册的候选名（`readPersistedActive`
   校验候选表，非法名打回 initial）。实测**内容不跨界**——B 的模型 prompt 里只有 B 自己的
   文本。是**路由态的完整性/可用性**问题，不是内容泄漏。

**准确的表述**：持久转交层的 key 只有一个会话维，而这个维在两个内置前端里被喂的是
**客户端可控值**，且框架在这一层没有提供任何归属协议（历史层有 `WithHistoryOwnerFunc`，
这里没有对应物）。

**成立条件四条，只有第 3 条特殊，1/2/4 都是默认形态**：① 命中同一份 store 视图（不需要
业务配外部 store）；② 编排名相同（同一个 app 的同一个 router 天然如此）；③ threadID 相同；
④ 目标候选在对方候选表里也存在。

**业务今天有出路**（约 20 行 `store.Store` 装饰器给所有 namespace 前置租户段，或每租户
独立 store 实例），且「租户 ID」是鉴权边界上业务手里就有的东西——按本仓「守卫合法性」
规约，**要求业务提供租户维是合法要求**。

**所以真正该做的是两件，都不是「加守卫」**：
- **写进契约**：`threadID` 会被当作转交持久态的唯一 key，而两个内置前端把客户端可控值
  直接接进去。这件事现在**一个字都没写**，而同一个仓在历史层对同一个值的处理是
  「必填 + panic + 专门的 OwnerFunc」。
- **补一条出路**：agui 形态下业务的自然出路被堵了（见 §5.9）。

### 5.9 【新发现·独立于 handoff】agui 的挂起会话按裸 threadId 索引，无归属维

`agui/handler.go` 的 `sessions map[string]*sessionEntry` 注释就写着 `threadId → 挂起会话状态`，
而 `in.ThreadID` 来自请求 JSON 的 `threadId`（客户端可控），`acquireForResume(in.ThreadID)`
直接拿它取挂起会话。**整个 agui 包没有任何一处提到鉴权 / 租户 / 归属。**

**已实测**：

```
A 起对话 → 挂起在 ask_user，interruptId="31e37628b00c3196"
B 只知 threadId，interruptId 故意猜错 + status="cancelled"  → outcome="success"
A 回来用正确的 interruptId 续跑                              → RUN_ERROR
```

**B 不需要知道 interruptId**——全 cancelled 走 `ResumeActionAbort` 终止，A 的挂起会话
连同 cp 一起没了。这是**拒绝服务**（读内容仍需 interruptId，所以不是内容泄漏），门槛
只有一个客户端自己就能构造的值。

⚠️ 这条**独立于 handoff**，是 agui 适配层自己的问题；`a2a/server` 的 taskID↔session
映射是否同形**未查**。

⚠️ 也是 §5.3 那条「业务的自然出路被堵了」的具体所在：`agui/handler.go` 对 threadID 是
**无条件覆盖**（只在空时才铸新的），且 `AgentFactory func(hooks) Agent` **连 request 都
拿不到**——业务想按租户改编排名或改 threadID 都做不到，只剩 store 装饰器一条路。



**已实测复现**：两个租户共用一个 store 后端（多租户部署常态）且递了同一个 threadID ⟹
租户 B 的**全新对话** `front` 被调用 **0 次**，直接进了租户 A 转交到的那个候选。

```
租户A 第1轮 final="A-billing 作答"（转给了 billing）
租户B 第1轮 final="B-billing 作答"；B-front 调用 0 次，B-billing 调用 1 次
```

ns 是 `(__handoff_active__, 编排名, threadID)`——`threadID` 来自 wire，**是续接标识不是
授权令牌**。⚠️ **这条规矩我们自己在历史层已经立过**（`history.go:78` 逐字写着「猜中别人的
就能拉到别人的完整对话」）并给了 `WithHistoryOwnerFunc`；转交持久层漏了。

**跨租户是真信任边界**，跟 §5.4 那个「同进程业务代码」的非边界不是一回事，**不该被同一个
「非目标」一起豁免掉**。

### 5.4 【修订】「非目标」的理由要换

- ❌ 旧理由「四条路都走不通」——不成立（见 §5.2）
- ✅ 新理由：**五家在库层无一设此边界**，而唯一被产品化的答案在**平台层**（按已认证主体
  在请求入口给 namespace 加前缀）。我们这层该做的不是发明一道守不住的守卫，是**把真边界
  指向正确的位置**。

顺带订正一句我自己写的、站不住的话：原注释说「强行加守卫的结果是框架自己也写不进去」——
那只是「把校验加在接口层」这一种实现的后果，框架完全可以自留特权路径（LangGraph 的 `batch`
/ MAF 的 `store.write` 都是）。真理由是「业务闭包直接捕获 `st`，没有可以放守卫的窄口」，
且那一句**足够**。第二句反而给了后来者一个可以反驳掉的靶子。已删。

### 5.5 【修订】能力授予：结论不变，理由要换

- ❌「MAF .NET 路径长度 0」——**不成立**。实际是 1，而且有两个洞：嵌套 workflow 当候选时
  `options` 参数**声明了却整个函数体不读**（静默丢）；官方推荐的装饰器基类**无条件透传**
  给内层（那正是我们测的「礼貌透传壳」，它的答案是**穿**）
- ❌「只有 eino 禁多挂」——**范围高估一半**。它的禁令只对实现了那个可选接口的对象生效；
  业务自实现 agent 多挂**静默放行 + 静默拿不到能力，两个静默叠在一起**
- ✅ **我们在一处上是五家里最好的**：`struct{ Agent }`（接口嵌入）这种最常见的业务壳，在
  「可选接口断言」那条路上**必然判否**（Go 只提升接口自己的方法集）⟹ 静默丢能力；而我们
  `sameEntity` 走反射匿名字段**穿透**（实测内层拿到能力），同时具名字段壳**不穿**。
  **那个静默面不是「往对象打标记」的通病，是「用可选接口断言当判据」的通病，我们这儿不存在。**
- ✅ 诚实的说法：存在第二条路（信号上行 + 逐层判地址），它**用授权换传递**；我们选的是
  **用传递换授权**。所以「N 个转授点」是**我们选的那条路的代价**，不是必然代价

### 5.6 【修订】信号载体：第一轮判词的成因说反了

第一轮说「有备忘 + 要求某类工具必须重跑，五家一个都没有」。实际是：**有一家有备忘，
且它的转交工具续跑时也不重跑**——它不出事是因为裁决结果和 payload 都在存档里。
**所以那个组合别家没有，不是别家避开了它，是别家的载体进存档之后它自动消失。**

并发裁决那条的正解是**消灭场景**（Parallel 成员不发授予），落点是**一个实参**——
`grant` 已经是位置参数、`nil` 已经是被文档化的合法值。论据用我们自己 `runDecisionAgent`
的 godoc：「一个负责判断该走哪个分支的模型没有资格改写这场对话归谁」，Parallel 的分支
处境相同。⚠️ **Sequential / Loop / Routing / Reflect 不该一起砍**——任一时刻只有一个
成员在跑，不存在并发裁决。

### 5.7 我们相对五家的净优势（别动）

- **转交环检测**：`maxHops` + 跨 Resume 正确恢复。一家环检测零命中（转交是递归调用，
  A↔B 会无界嵌套）、一家唯一的计数器**恰好在转交时归零**、一家的等价物更粗（数轮次不数跳数）
- **has-a 透传的拒绝**：五家里独有的精度（最接近的对应物是无条件透传，靠作者自觉）
