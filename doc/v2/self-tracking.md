## 0. 决策记录（2026-08-27 拍板）

### ⭐ 先看这一条：**(c) 写收窄是整个方案的地基**

四条决策里有**三条的安全性最后都落在它上面**。它从「ns 分区的一个选项」变成了前提：

| 依赖它的决策 | 没有它会怎样 |
|---|---|
| **A 全开** | 便签变多写入者 ⟹ 覆盖式写不安全 |
| **B 不注索引** | 地址不再是「模型身份的确定性函数」⟹ 模型不知道去哪找 ⟹ **必须**注索引 |
| **D 来源标记** | 标记可被其他写入者伪造 ⟹ 退化成装饰 |

**(c) 的定义**：**写**收窄到自己那一格（写入者段由框架加、**不进模型面写路径**）；**读**可跨格
但**只读**（跨格读回来的条目带写入者段才定位得回）。可行性已核：现有 `store.Store` **零改动**
可实现（`Item` 自带 `Namespace`+`Key`、`Search` 是前缀语义 ⟹ `Get` 精确读得回）。

### 四条决策

| # | 决策 | 理由（**注意：多条的理由在第 10-11 轮被换过**）|
|---|---|---|
| **A** | **写/改全开，不做 append-only** | 判据是「**有几个写入者**」——(c) 之下每条便签**只有一个写入者**。⚠️ **初稿的理由「业内是单写入者」是错的**（实测那家**允许跨 agent 写**），它敢全开靠的是**自动按写入者分域**，而 (c) 正是那道护栏 |
| **B** | **不注入索引**（只给工具 + 一段常数大小的指导词）| 判据是「**模型需要时去查 vs 不查也必须生效**」。便签属前者。⚠️ **初稿的两条理由全错**：「4:1 主流不注入」是**反的**（重数约 9:1:1:2 偏注入）、「触发时机模型察觉得到」也**被推翻** |
| **C** | **分层**：`store.Store` 库层不碰身份 / 平台层 push / **便签 ns 计算处折** | 业内库层 8 家**都不折**，平台层才折。⚠️ 两家各有一个租户边界，但**都是从部署形态白拿的**（认证 token / OS home）——**我们的共享 KV store 没这便宜** |
| **D** | **来源标记**，且**由框架从写入者位置派生** | 便签会被读回上下文 ⟹ **能写便签 = 有一条向未来注入的通道**。⚠️ 理由不是「溯源」是「**不可信输入标记**」；且**模型不能自己写这个标记**，否则可伪造 |

### B 成立的三个前提（缺一就得改注索引）

| # | 前提 | 状态 |
|---|---|---|
| ① | 便签地址是**模型身份的确定性函数**，且身份已在上下文里 | ✅ **(c) 提供** |
| ② | 列表工具**零必填参数**，默认作用域即「我自己的」 | ✅ 设计上直接满足 |
| ③ | 一段**常数大小**的指导词讲清「什么时候该去读」 | ⚠️ **要写** |

> ⚠️ **索引的真实价值只是省一次 round-trip**，而代价**正比于条目数、且每次都付**。
> ⭐ 另有一个更好的形态在特定时刻可用——**就地指针**（内容被移走时，在原位留 locator +
> 取回方式）。**我们已经有这个机制**：`MicroCompact` 的 offload 就是「挪走 + 原地留占位符 + key」。
> 它够用的原因是结构性的：**指针坐在模型本来就要看的位置上，「我什么时候该去查」这个决策
> 根本不存在**。

### 两条已知缺口（一期不做，但别当成方案已完整）

- **零淘汰机制**——业内按「**有没有被真正引用**」淘汰、30 天未引用即删。调研原话：这是「最容易被省掉、**也最不该省**的一环」。
- **无来源污染闸门**——业内有「碰过外部不可信来源就不产记忆 + **追溯删除**」。我们有 MCP / `tool_search` / 沙箱，**同样的暴露面**。

### 一条可直接当验收标准的

> ① 会话 A 调写工具成功 → ② **全新会话 B，同一存储作用域下检索拿到那个值，且不带 A 的 transcript**
> → ③ B 在后续回答里用上了它。

第 ② 条的「**不带 A 的 transcript**」是关键——它**排除了「其实是靠历史串过来的」这种假绿**。

## 1. 先纠正一个分组错误

最初把「历史检索 / notes / goal」当**一组**记进 backlog。**这个分组是错的**，三家的目录结构给出
一致的反证：

| | 历史检索 | notes | goal |
|---|---|---|---|
| A 家 | 同一个 crate、同一套存储、**同一句 prompt 政策** | 同左 | **另一个 crate、另一套存储、另一组生命周期钩子** |
| B 家 | 独立包组（4 包） | **没有**（`packages/` 与 45 篇子系统文档零命中；其答案是「共享工作区即长期记忆」，模型用现成的读写文件工具）| 独立包组（4 包）|
| C 家 | 仅作为记忆的子功能 | 两种形态（模型自写 / 框架提炼）| **没有**（用 todo + mode 顶）|

**正确的分组是二比一**：

- **历史检索 + notes 是一组**——它们回答同一个问题：**被挤出上下文的东西怎么办**。两种策略：
  事后捞回原件（检索）vs 事前存个提炼件（notes）。
- **goal 不是记忆问题，是控制流问题**——它的产出是「满足条件时再跑一轮」。B 家的设计记录里明确
  拒绝过「把 goal 塞进 agent loop」。混进同一个方案会污染两边。

本文按这个分组写：§3 一组，§4 单列。

> ⚠️ **本表与 [harness-survey.md](../description/three-way-comparison/harness-survey.md) 那篇的 §8.4 旧表
> 冲突过，以本表为准**——那边曾把 Codex 的 notes 工具记到 B 家头上（于是「三种范式」实际只有两种），
> 已于 2026-08-21 核源码后订正。

## 2. 我们的地基（逐条 grep 核实，2026-08-21）

方案的可行性取决于现有件。**好消息是最难的部分已经有了。**

| 件 | 现状 | 对方案的意义 |
|---|---|---|
| `HistoryStore` | 只有 `Append` / `Load`，key = `HistoryKey{Owner, ConvID}`，**append-only 硬约定** | 逐字流在，但 `Load` 返**全部**、无检索、无有界读 |
| **压缩不改历史写入** | 更硬的依据不是那句 godoc，而是**写入点写的是什么**：model 节点写的是**本轮 LLM 产出**（`basic_builder.go:505`，注释「本轮 LLM 产出」），tools 节点写的是**本轮全部工具结果**（`:666`）——**都是这一轮新产生的东西**；压缩只作用于**喂给 LLM 的输入**，与写入无关 | ⭐ **HistoryStore 里留着的就是完整逐字流**——B 家花一整套 fold + 遮蔽标记才拿到的东西，我们因结构而天然具备 |
| `store.Store` | `Get` / `Put` / `Delete` / `Search` / `ListNamespaces` / `Batch`；`Search` 带 `WithQuery`（语义检索 seam）+ `WithFilter` + `WithLimit`，`SearchItem` 带 `Score` | **可改写的知识层，检索能力现成** |
| MicroCompact offload | 原文已 `store.Put`，key 挂在占位符的 `MicroCompactOffloadKeyAnnotation` 上 | 取回通道**在框架侧**已通（`store.Get(NS, key)`）。⚠️ 但 offload 用的是**框架私有 NS + 框架 key schema**（`_micro_offload/<sid>`，key 是 tool_use_id），与便签的 NS/key **两套键空间不相交**——一套按便签路径列/读/搜的工具**读不到任何 offload 内容**。框架 godoc 也明说那是**另一件工具**（业务自注册、框架不自动 inject），且该路径默认关 |
| 框架工具范式 | `WithAskUser()` 式 Option 声明、框架每次 Run 注入（`withFrameworkTools`，不写进业务传进来的 toolkit——它可能被几个 agent 共用）；「框架铸的」封闭标记（`agent_v2/framework_tool.go`，2026-10-12 前是 `isFrameworkTool` 名字名单）在多处**改变语义**——大多数是豁免（审批 / ToolFilter / 渐进披露的 bind 与 dispatch 两侧 / 工具中间件与超时 / 结果截断 / 重复调用检测），**工具账方向相反**：`shouldMemoize` 是 `signals.Len() > 0 || !minted`，**带标记 = 不进 tool_call memo = Resume 时工具体重跑**。加新工具前须 grep `isFrameworkMinted` 的全部调用点 | 加新框架工具有现成范式，**新工具必须带那个标记**（绑定侧与派发侧注册的两件都要带）|
| `LoopAgent` | `LoopAgentExitCondition func(ctx, lastOutput *schema.Message, round int) (bool, error)`，经 `WithLoopExitCondition` 装配 | ⭐ goal 的「续跑」**不需要新循环原语** |
| 两层存储分工 | History = **逐字流、不可改写**；store = **知识层、可改写** | **决定每样落在哪边**（见 §3.1） |

## 3. 第一组：notes + 历史检索

### 3.1 落点由「可不可改写」决定，不是由「像不像记忆」决定

- **notes 落 `store.Store`**——模型要能改、能删、能重写；`HistoryStore` 是 append-only 硬约定，
  放那儿的话「改一条便签」在结构上就不可能。
- **历史检索落 `HistoryStore`**——它检索的对象就是逐字流本身，而那只在 History 侧。

⚠️ **别把两者合进一个存储图省事**：一个必须可变、一个必须不可变，合并等于让其中一半破约。

### 3.1b ⭐ 这个方案到底补什么洞（第 10 轮才说清，前九轮都没答准）

**先承认前九轮的问题**：文档一直用「模型对自己干过什么没有可读写的面」来论证，那句话**不准确**——
我们**已经有** `sandbox.NewBashTool(sb)`，它给模型的就是完整读写改（工具描述里逐条映射好了：
`cat` 读 / `cat > <<'EOF'` 写 / `sed -i` 改 / `find` 找 / `grep` 搜），而且是「唯一沙箱执行入口」。

**真正的洞在可用性前提上**（第 10 轮 grep 实测）：`sandbox.Sandbox` 接口全仓**没有内置实现**——
只有接口和 `sandbox_bash` 工具，后端（远端 HTTP 沙箱等）由业务自接。**没有本地 / 进程内实现。**

| 业务有没有沙箱后端 | 模型能不能自己存点东西留着 |
|---|---|
| **有**（业务接了沙箱后端，自实现了 `Exec`）| ✅ **能**——`sandbox_bash` 全套读写改，**这个方案对他们价值有限** |
| **没有**（只有 LLM + 业务工具）| ❌ **完全不能**——一点都存不下来 |

⟹ **便签跑在 `store.Store` 上**（InMemory / Redis / PG 都行），**不需要沙箱后端**。这才是它相对
通用文件工具的实质增量：**可用性前提完全不同**。

⚠️ **两条由此而来的设计推论**：
1. **默认关是对的，但理由变了**——不是「怕模型乱用」，而是**接了沙箱的业务本来就不需要它**。
2. **别做成沙箱的替代品**。它的定位是「**没有沙箱时的最小持久面**」，所以功能上**应当明显弱于**
   `sandbox_bash`（没有任意目录、没有管道、没有脚本执行）。**一旦开始往那个方向长，就是越界**
   （§5 那条判据）。

### 3.1c ⭐ 三个成立条件——我们中了两个（第 10 轮，**这节替代前九轮所有「为什么做」的论证**）

调研给出了「**专门便签层相对通用文件工具，什么时候才有实质增量**」的三个精确条件。**逐条对我们验**：

| 条件 | 何时成立 | 我们 | 证据 |
|---|---|---|---|
| **① 审批姿态反转** | 业务开了 `ApprovalAsk` | ✅ **成立** | `sandbox_bash` **不在** `isFrameworkTool` 名单（`approval.go` 零命中）⟹ 开审批后模型**每写一次便签都要问用户一次**。而同一个 `sandbox_bash` **无法**表达「写便签免审批、写别处要审批」 |
| **② 写入形态受限** | 要「只许追加、不许改写」 | ❌ **不成立** | §0 决策 A 已决：写 / 改全开、不做 append-only（原注：shell 结构上给不了 `create_new` + 文件名正则这类不变量） |
| **③ 脱离文件系统** | 便签要跨进程 / 不依赖沙箱 | ✅ **成立** | `Sandbox` 接口**全仓只有一个远端实现**（§3.1b）；便签落 `store.Store`，有 `redis` / `sql` 后端 |

⟹ **两条成立即可动手**，且它们**恰好互相独立**（一条关权限、一条关可用性）。

#### 更要紧的：我们已经有它的两个邻居，别做重了

| | 模型能主动控制 | 要沙箱后端 | 吃审批 |
|---|---|---|---|
| `sandbox_bash` | ✅ 全套读写改 | ❌ **要** | ❌ **要**（不在豁免名单）|
| **便签（提议中）** | ✅ | ✅ **不要** | ✅ **不吃**（进名单）|
| `WithStoreMemory` | ❌ **零**——框架 preamble 自动 `Search` 注入、postamble 自动 `Put` | ✅ 不要 | ✅ 不吃 |

⟹ **便签要占的格子很窄且明确**：**模型能主动控制** + **不要沙箱** + **不吃审批**。三者缺一它就退化成邻居之一。

⚠️ **两条由此而来的红线**：
1. **别加自动注入 / 自动保存**——那是 `WithStoreMemory` 的活，加了就是重复造。（这与 §3.2e 决策 2「不注入索引」**同向**。）
2. **别加任意目录 / 管道 / 脚本执行**——那是 `sandbox_bash` 的活。**功能上应当明显弱于它。**

### 3.1d ✅ **已决：主 agent 直接写**（2026-08-27）——它定死后面所有答案

> ⚠️ **第 11 轮补充**：这个决策**和决策 A 是同一个决策的两面**。Codex 证明「谁写」与
> 「可不可改写」不正交——判据只有一句：**这份数据有几个写入者**。**1 个** ⟹ 不需要
> immutability（本决策 + A 全开）；**2 个**（agent + 离线整理器）⟹ 立刻要划分所有权。
> 我们选 1 个，所以两条一起答完。见 §0。

调研的第一句话就是：**「便签」在这批实现里分成两派，而问题在两派里不是同一个问题。**

| | **主 agent 直接写** | **离线写手 agent 写** |
|---|---|---|
| 谁 | 两家 | 两家（同一套 prompt 的两个分支）|
| 主 agent 的写权限 | 全套 | **只有一个「投递箱」**——投完不管，等离线管道消化 |
| 给模型的写作指导 | **几乎没有**（一家的全部指导是一句 docstring）| **极详尽**（一家约 60KB，含禁用措辞黑名单、认识论标注要求、保留原字面量规则）|
| 触发条件 | 泛指「值得记的」 | **只有用户明说 remember / forget / update 三个动词** |
| 整理 / 合并 | 无 或 写入时同步做 | 离线两阶段 + 全局锁 + git baseline |

⚠️ **关键观察：那 95% 的文字量在写手那套里，而写手根本不参与对话。** 也就是说——**详尽的写作指导之所以存在，是因为有一个专职的、只干这一件事的读者**。让主 agent 边干活边遵守 60KB 规范是不现实的，所以主 agent 那派**干脆什么都不规定**。

⟹ **这是一道必须先答的题，因为它连带定死**：要不要写作指导（以及能写多详细）/ 要不要 frontmatter / 触发条件写多窄 / 要不要整理管线。

**我的推荐：主 agent 直接写，且明确接受「无写作指导」的后果。**
- 离线写手那派要一整条管线（两阶段 + 状态库 + 租约 + git baseline + 子 agent 编排，一家约 4000 行 + 82KB 模板），**远超 §5 那条「补入口不建子系统」的判据**。
- 而主 agent 那派最便宜的一家**只有 524 行**，且大半是把通用层的函数换个作用域再包一遍。
- ⚠️ **代价要认**：便签会长得杂乱、无结构、无人整理。**这是选了这条路就得接受的**，别指望靠 prompt 补回来——两家主 agent 派都试过了，给的指导都少到不成比例。

### 3.1e 两条可直接抄的具体做法（第 10 轮）

**(1) ⚠️ 解析层防伪造分节符——只有一家做了，而它防的是 prompt 层防不住的。**

五家里四家有 prompt 层的「这是数据不是指令」框定（我们的 `sandbox_bash` 也有，`bashSecurityNote`）。
但**只有一家做了解析层防护**：写入前把行首像标题的行转义掉，注释写明动机——**便签被回读时，内容里
的 `## Memories` 会被自己的 parser 当成真的分节符**。

⟹ **这条我们躲不掉**：便签正文注入回上下文时，只要我们用任何结构化包裹（标题 / 分隔符 / 标签），
模型写的内容就能伪造它。**我们的 `sandbox_bash` 已经用了随机 nonce 标签**
（`<sandbox_output_XXXX>`，每次随机）——**便签应当复用同一个手法**，比转义更强（伪造者猜不到 nonce）。

**(2) 超限时要让模型知道，别静默截断。**
调研横向对比里，**只有一家给了模型可执行的出路**——工具描述里写「接近上限前另起一个文件」。
其余全是**静默截断**（一家的索引第 51 条起直接不显示、另一家读回来超 token 就砍）——**模型不知道
自己丢了东西**。
⟹ 便签的读 / 列工具**超限时必须显式告诉模型「还有更多、请缩小范围」**，而不是悄悄返回一部分。
（⚠️ 这与 §3.2b(1) 对策 ① 「读类工具返回有界内容」是同一件事的两半：**有界是必须的，但边界要可见**。）

### 3.1f 失败模式与事后护栏（第 10 轮第四路，**含一条反对本文推荐的证据**）

这一路专挖「**被现实教育出来的东西**」——那些看起来多余的防御、奇怪的 prompt 句子、事后补的开关。

#### ⚠️ 先摆冲突：证据反对 §3.1d 的「主 agent 直接写」

调研的独立结论是「**模型不能直接写记忆**」——最成熟那家的 prompt 逐字：「**只有**用户明确要求时才能更新记忆」
+「**不要自己编辑记忆文件**，只能投一张便签」。写入走离线管道，模型投的便签 **7 天后被回收**。

**它给的理由是一条我没想到的危险**：那个离线写手被配置成 `ephemeral = true` + 关掉自己的记忆生成，
注释写明动机——**记忆写手自己的会话记录会被下一轮当成素材，形成自我放大回路**。

⟹ **两个推荐冲突，必须由人拍板**：

| | §3.1d 推荐（主 agent 直接写）| 本节证据（离线写手）|
|---|---|---|
| 依据 | **成本**：主 agent 派最便宜一家 524 行；写手派一家约 4000 行 + 82KB 模板 | **质量与安全**：详尽写作指导只对专职读者有效；且能隔离自我放大回路 |
| 与 §5 判据 | ✅ 「补入口不建子系统」 | ❌ **明显是建子系统** |

**✅ 已决：主 agent 直接写**，理由是那条离线管线**整条超出本方案的判据**（「补入口不建子系统」）；**代价明确接受**：
放弃写作质量控制、放弃自我放大回路的隔离（⚠️ **我们这边这条风险较小**——我们不打算把 agent 自己的
会话记录当素材，只存模型显式写的东西）。

#### 五家全部默认关，且最成熟那家在「稳定」之后仍坚持不默认开

那家的 feature 已标 Stable，**却仍写着 `default_enabled: false`**，commit 说明逐字：「**它应当保持
opt-in**」——同时**不出任何公开文档**。⟹ 与本文「必须 opt-in、默认关」的结论一致，且理由更硬。

#### 四条我们该抄 / 该知道的具体护栏

| 护栏 | 它防什么 | 对我们 |
|---|---|---|
| **来源污染闸门** | 「这次会话碰过外部不可信来源 ⟹ 不许产生记忆」，且**追溯删除**已生成的。原字段名是化石：「用过 MCP 或 web search 就不要记忆」 | ⚠️ **我们有 MCP、有 `tool_search`、有沙箱**——同样的暴露面。**一期可以不做，但要记为已知缺口** |
| **按「有没有被真正引用」淘汰** | 不是按写入时间。要求读出侧**强制模型报引用**，30 天没被引用就物理删除 | ⚠️ **我们的设计目前零淘汰机制**——便签只增不减。这是**已知缺口**，且调研说这是「最容易被省掉、也最不该省的一环」 |
| **格式注入防护** | 便签正文里的 `##` 会伪造出真的分节符 | ✅ 已在 §3.1e 记录——复用 `sandbox_bash` 的随机 nonce 手法 |
| **符号链接逃逸** | 那家出过真实安全 fix：LLM 在记忆目录里建符号链接，后续写入跑出沙箱 | ✅ **我们天然免疫**——便签落 `store.Store` 的 KV，**根本没有文件系统** |

#### 成本数字（决定「默认关」是不是够）

- 那家的**常驻** prompt 开销：注入摘要 ≤2500 token + 指令本体约 1.2k ⟹ **每请求 ≈3.5–4k token**
- 离线整理一次要跑到 **500 个 agent turn**；并且配了一道闸——**用户配额低于 25% 就整体跳过**（烧的是用户自己的额度）
- 另一家出过**已上线的成本 bug**：把 1536 维 embedding 一起塞进召回内容给模型，「**每条召回白烧上万 token、零价值**」

⟹ **我们采纳「不注入索引」（§3.2e 决策 2）之后，常驻开销 ≈ 只有工具 schema**，这是那 3.5–4k 的
主要来源被砍掉了——**这条反过来强化了决策 2**。

#### 两条「别指望」

1. **别指望模型会自己想起来查**——三家都不得不写决策树 + 预算上限；有一家直说「**如果工具描述
   触发不可靠**，请自己往 system prompt 里加一句提醒」。
2. **别指望有现成默认参数可抄**——**最关键的那个旋钮（去重多狠）同一批人在两个仓库里调向相反**：
   一处写「激进去重、宁可少而锐」，另一处写「宁可广而全，别把 5-10 条当隐含目标」。**没收敛。**

### 3.2 notes——先做这个

**为什么先做**：**不引入新的框架机制**、不碰压缩层、不碰 cp，而 `store.Store` 已经把最难的部分
（可插拔后端 + namespace + 检索 + conformance 套）做完了。

⚠️ 但**别把它说成「零改动」**——实际要碰的位置（照 `ask_user` 那套量的）：新常量 + 工具定义 +
带「框架铸的」标记三处是纯增量；而 **preamble 注入索引**和**把写类工具排除出并行扇出**这两项
**要动既有节点逻辑**。总量仍小，但不是零。

> ⚠️ **采纳 §3.2e 决策 2 后「索引注入」整项不做** ⟹ 「要动既有节点逻辑」只剩**「写类工具排除并行
> 扇出」一项**。⚠️ 而一期若连「追加」也不做（§6），连这一项都可能不需要——**估工作量前先看 §6**。

**形状**（形状为主，签名待实现时定）：

- 一个 Option 开启，注册 4–5 个框架工具：列出 / 读 / 写 / 追加 / 检索
- 存储直接用 `store.Store`，命名空间用 `store.NS(...)`。⚠️ **可见性不能照抄「写入者维进 ns」那套
  ——见 §3.2c，那是一道必须动手前定死的选择**

> ⚠️ **就算最后决定复用 ns 规则，也别连 key 方案一起抄。** 那套 ns 规则是好的，可它当时配的 key 是
> `<RunID>_assistant_<这条流里的第几条>`（`basic_agent.go:1830`，格式注释在 `:1825`）：**同一个写入者在一次任务里被调
> 多次时**（`AgentAsTool` 调两次 / `RunSubAgent` 循环 / 图级 fanout），若各自新建 child session，
> 序号各自从头数 ⟹ **撞键、后写覆盖先写**（这个缺陷已于 2026-08-27 由 `ba629eef` 修掉：键换成 `<RunID>_assistant_<内容指纹>`；教训仍成立）。
> **便签天然能规避**——它的 key 是**模型给的便签路径**，本就不依赖序号。别在便签这边重新引入
> 一个「按顺序编号」的键。
- ⚠️ **便签工具绝不能命名为 `Read` / `Write`**——那会**隐式**落进 `DefaultCompactableTools` 默认白名单
  （§3.2b(1) 对策 ② 那条路），**却没有它要求的配套工具描述**（「模型必须能重读」）。要走 ② 就
  **显式**写进 `CompactableTools`，别靠撞名。
- **带「框架铸的」标记**（2026-10-12 前叫「进 `isFrameworkTool` 名单」）——**业务开了审批 / ToolFilter / 渐进披露 / 工具中间件链中任何一档时**，不带标记就会被拦、被裁、要先被「揭示」才能用、或被中间件包一层（四者默认关，所以不是默认路径问题）

> ⚠️ **但这不是「顺带的好处」，是一个要显式记录的决策。** 审批那一格的豁免有**它自己的理由**——
> 「审批针对业务工具，框架元工具审批**无意义**」，而那个理由对**写便签**不成立：它会往**业务自己
> 的 `store.Store` 后端**落持久数据（存储成本 / 内容合规 / 多租户），跟 `route_to` / `final_output`
> 那种纯控制流不是一类。
>
> 更要紧的是**豁免排在业务策略之前**：派发的那件带标记就直接 `proceed`
> （`checkToolApproval` 的 `minted` 分支），`cfg.ApprovalHeuristic`**根本没机会看到这次调用** ⟹ 开了
> `ApprovalAsk` 的业务**看不到也拦不住**模型写便签，连「只对写类便签要审批」都做不到。
> （先例是 `run_skill_action`——同样有外部副作用、同样在名单里，所以不是全新问题，但**是未记录的
> 决策**。）若不可接受，就单开一条「写类便签需要独立审批通路」进 backlog。

> ⚠️ **HIGH：带标记有一个方向相反的副作用，写类便签工具必须先解决它。**
> 那几个调用点里，`shouldMemoize` 是 `signals.Len() > 0 || !minted`（`agent_v2/tool_memo.go`）——
> **带标记又没做出上行信号 = 不进 tool_call memo = Resume 时工具体重跑**（这是刻意的，`tool_search` 靠重跑
> 补回它写 RunSession 的那半）。对「列出 / 读 / 检索」无害，对**「写 / 追加」有害**：便签落
> `store.Store`，追加是 read-modify-write，重跑一次就多追加一份，而 **`err == nil`**。
>
> ⚠️ **「写类工具不并行」挡不住它**——tools 是**整节点原子**的（`basic_builder.go:663-665`：
> 任一工具抛中断/报错会让这批 writes 全部作废、Resume 时**没进 memo 的**全部重跑），只要同轮里**任何**兄弟
> 工具中断（`ask_user`、审批），写便签那次照样重跑。
>
> **出路只剩一条**：把写/追加做成**幂等**（内容寻址 key，或要求模型带 write-id）。
>
> ⚠️ **初稿给的第二条出路「工具自己声明控制效果、让框架重放」已不存在，已划掉。** 那套声明机制
> （`tool.ControlEffectMetaKey`）已删：进得了工具账的「tool_result 之外的产出」现在只有框架入口做出的
> 转交 / 路由决定（上行信号，随账记下、命中时交出，见 `compose_v2/signal.go`），只能经框架入口做出
> （收件人由引擎铸，业务工具算不出来）。便签那半要走通只能新增一类框架信号——这与一期「不引入新的框架
> 机制」的立项理由直接冲突。
>
> 语义上也不该走那条：转交 / 路由决定要随账记下，是因为它们的真产出**在 tool_result 之外、需要交给
> 上方**；便签的产出在 `store.Store` 里，重跑时本来就还在——**没有东西可交**。
- 注入一份**有界的索引**（有哪些便签、各是什么），别把正文全塞进去。⚠️ **但「注在哪」是第二个
  必须现在定的二选一**——初稿写「preamble 注入」，没论证；而同一个仓库里 `WithAgentsMD` 面对
  **同一道题**（每轮都要在场的 harness 级上下文）选了**每轮 transient 注入**，并在 godoc 里逐条
  列了理由：「①不被 4 层压缩 summarize（每轮在压缩**之后**注入）②Resume 自动重注入③无需幂等
  marker / 压缩保护」。

> ⚠️ **第①条对便签索引尤其致命，因为它把 §3.2b(1) 的缓解措施抽空了。** `preamble` **只跑首轮**
> （`basic_builder.go`：「preamble 只跑首轮（tools→model 直接回，不经 preamble）」）⟹ 索引是
> **首轮快照**，模型第 3 轮写的便签**不会出现在里面**。长跑到后半段就是「内容看不见 + 目录也不
> 更新」的两半失明。而且 preamble 的产出是**持久消息**（写进 `basicMessagesCh`）、**进压缩范围**。
>
> ⚠️ **(a) 业内零先例；(b) 的「压缩豁免」其实有先例（见 §3.2e 表）。调研推荐「都不选：不注入索引」——见 §3.2e。**
> 下面两个选项保留作对照：
>
> **⟹ 二选一**：**(a) 照 AgentsMD 做 transient 每轮注入**——天然免疫压缩 / Resume 自动重注 /
> 无需 marker / 索引每轮反映最新状态，代价是每轮多一次 store 查询；**(b) 留在 preamble**——那就
> **必须补两件**：跨层压缩 marker（照 `StoreInjectedAnnotation` 那套），以及在工具描述里声明
> 「索引只反映本次调用起点，本轮内新写的不在里面」。**现在两件都没写。**

**三条从外部直接取的约定**：

1. **写类工具不参与并行扇出**。我们的 tools 节点在 `len(toolCalls) == 1` 时 inline 跑、**N≥2 才起 goroutine 并发**（ISSUE-81），而两家都把
   写类工具排除在并行之外。
2. **单条容量给上限，并且把上限告诉模型**——A 家给的是「接近上限前另起一个文件」，即让模型自己
   分片，而不是框架截断。
3. **prompt 里声明这是模型私有状态**：使用它但不要向用户描述这个工具、它的存在、路径或内容。
   ⚠️ 这类措辞是外部踩过很多次才攒出来的，**抄机制时顺手抄措辞是白捡的**。

**⭐ 与现有 offload 天然配套**：外部把 notes 定位成「压缩的卸载靶子」，而我们的 `MicroCompact`
offload **已经在做同一件事**（大内容挪进 store、原地留占位符 + key）。给模型一个读写**同一个
store** 的入口，等于把第 1 层压缩从「框架替你挪」升级成「模型自己决定挪什么」，两者共用一个后端。

> ⚠️ 初稿这里写的是「一个我们独有、三家都没有的组合」——**那是没有证据的全称否定，已撤**。
> 调研只记了「外部把 notes 当卸载靶子」，**没有核过它们有没有让模型读写同一个卸载存储**。
> 想主张「独有」得先去核那一条。

### 3.2b 五个方案原本漏掉的面（第四轮审补）

前三轮查的都是「写了的对不对」，这一轮查「该写而没写的」。以下五条**动手前必须有答案**。

**(1) 便签的读结果默认**不会**被第 1 层压缩清掉——真正要防的是反面。**

> ⚠️ **本条初稿写反了，且是「最要命」那条，2026-08-26 独立核实后重写。** 原文的推理是
> 「`microcompact.go` 全文无 `isFrameworkTool` 判断 ⟹ 对框架工具零豁免」。**前提属实、结论错**：
> 豁免存在，只是**不以 `isFrameworkTool` 的形式**——是一张**工具名白名单**
> （`microcompact.go:186-193`；空则回落 `DefaultCompactableTools`）。这是「查了一种形态没命中
> 就下全称结论」的典型，本仓 CLAUDE.md 记过同款病。

事实：`MicroCompact` **只清白名单内的工具**——`whitelist[tc.Function.Name]` 不命中的连
`perToolIDs` 都进不去（`microcompact.go:203`），自然进不了待清集合。默认白名单
`DefaultCompactableTools` 是 8 个内置工具（`Read/Bash/Grep/Glob/WebSearch/WebFetch/Edit/Write`，
`:124-127`），**一个框架工具都没有**，godoc 也明写不在白名单的东西「需要用户显式 opt-in」。

⟹ **设计含义要反过来读**：

- ✅ 便签**不需要**被设计成「假设上次读的内容已被清掉」——默认它还在。
- ⚠️ **真正的风险是它永不被清**：模型每读一次便签，一份**完整正文**就永久留在上下文里；同一条
  便签读 10 次 = 10 份副本，而第 1 层压缩**默认不会**替你收拾。这跟「便签是用来省上下文的」
  初衷正好相反。
- ⟹ **两条对策（动手前定）**——⚠️ **采纳 §3.2e 决策 2 后不是二选一**：那边论证了 **② 为主、① 为补**（病因在调用次数、① 只压单次体量）：① 让**读**类工具返回**有界**内容（长便签返回摘要 + 明确的
  再取方式），把体量控制在工具自己这一侧；② 把便签工具**显式写进 `CompactableTools`**——此时才需要**新立**一条约束：
  **模型必须能重读**（本条订正前的初稿正是按这个假设写的，那段文字已被上面的订正块替换），
  要一并写进工具描述。
- ⚠️ **别选「什么都不做」**——那是默认路径，而默认路径在这件事上是会漏的那个。

**(2) 便签内容会在历史里存两份——而初稿把代价记轻了。** tools 节点**无条件**把本轮全部工具结果
写进历史（`basic_builder.go:666`，无豁免判断、逐字不截断）⟹ 写便签的 `tool_result` 进历史、便签
本体进 store。初稿只记了「三期做检索时可能搜到自己写的便签」，**实际有两个更早、更实的后果**：

- ⚠️ **「模型能删便签」（§3.1）只删得掉 store 那一份。** `HistoryStore` 只有 `Append` / `Load`
  ——**没有删除**，历史里那份**全文永久固化、也没有接口能删**。这对 §3.2b(4) 要讨论的私有性 /
  合规是**实质削弱**，比「三期可能搜到」严重得多。⟹ 工具描述里「删除」的语义边界要写清：删的是
  **可读回的那份**，不是逐字流里的那份。
- ⚠️ **一期就有的 token 代价**：开了历史层后 `prior` 换源为历史逐字流 ⟹ 每次写便签的**全文**
  `tool_result`，从下一个 Run 起作为 prior 重新进 prompt，**随 Run 数累积**。而便签的卖点正是
  「提炼件替代全文」——**这个组合把省下的又灌回去了**。第 0 层 `MaxHistoryPairs` /
  `HistoryCompactor` 能截，但那是业务 opt-in、**按条数截、不区分便签**。**已记进 §6 一期的代价栏。**

**(2b) 两个小但会绊人的边界。**

- **skill fork 默认路径下便签工具不在**——默认 fork 子 agent 只带三件 option
  （`WithName + WithSystemPrompt + WithModel`），隔离契约明写**不继承** parent 的 Hooks / Memory /
  **Toolkit** ⟹ **便签能力不随 fork 传播**。走 resolver 且子 agent 自己配了便签时才在，落
  `基准ns/__skillfork_<skill名>`（双下划线 sentinel 段）。父看不看得见**取决于 §3.2c 那个未定的
  读侧决定**。
- **便签工具在 `WithToolMiddleware` 链之外**——框架工具**不过链**
  （`basic_agent.go:2666` 的 `&& !isFrameworkTool(...)`）⟹ §3.2b(4) 说的观测**必须走
  `hook.Hooks` 的 `OnToolStart/End`**（那一侧无豁免、全部 tool_call 都 fire），业务想用中间件做
  限流 / 脱敏 / 短路便签写入**也做不到**。

**(3) 写失败怎么办。** `store.Put` 返 error。⚠️ 参照**历史层是旁路**（写失败吞掉 + warn、不打断
主链路）而**便签不是**——模型明确要求「记下来」，静默失败会让它以为记住了。**建议**：写失败要作为
**工具级错误**返回给模型（让它知道没记上、可以重试或改用别的方式），而不是吞掉。

**(4) 可观测性缺口。** 便签是模型**私有**的（外部那句 prompt 政策就是「never disclose to the user」），
但运维需要知道「它写了多少、写了什么」。⟹ 至少要有 metric（写入次数 / 大小），trace 里是否记内容
**需要拍板**（记 = 私有性打折，不记 = 出问题查不了）。

**(5) 业务迁移。** 这三样都是 **opt-in 新增**，不改任何现有签名 ⟹ **存量业务零影响**。⚠️ 唯一例外
是三期：给 `HistoryStore` 加方法会**破接口契约**，所有业务自研 backend 必须跟着改——这也是三期
排最后、且要「先定对形状」的原因。

### 3.2c ⚠️ HIGH：ns 方案是**动手前必须定死的一道选择**（三选一），不能照抄 StoreMemory

**这一整节是第六轮三个独立 agent 各自撞上同一条规则审出来的，前五轮全漏。** 那套规则有**两个面**
都不适配便签，且是同一个根因：**它写侧分区、读侧不收窄**。

#### (i) read-modify-write 会静默分叉

StoreMemory 能用那套规则，靠的是**三个前提**：只追加 / 键由框架铸（`<RunID>_assistant_<n>`）/
**模型从不改写**。而 §3.1 明写便签「模型要能改、能删、能重写」——**三条一条都不满足**。

后果：模型 `list` 到 `基准ns/br1/todo.md`、读出来、改完写回 ⟹ 写落在**它自己那一格**
`基准ns/br2/todo.md`，原件仍在 br1。**同一条便签两份、模型以为更新了、`err == nil`。**
⚠️ 而便签的键是**模型给的语义路径**——`todo.md` / `notes.md` 这种名字**任何 agent 都会选**，
**撞名是常态不是例外**。

**同一个根因的第二个面**：`Search` 是**前缀**（含全部后代）而 `Get` 是**精确 ns**，且不存在时返
`(nil, nil)` **不返错** ⟹ 模型 list 到一条别人写的便签、再按路径 read，拿到**静默空**。
⟹ 模型面的「便签路径」必须是**读得回来的完整定位**（要么全局单一 ns 让路径就是 key，要么路径里
含写入者段，**要么读写两侧用同一个收窄后的 ns**——即 (b)，写入者段由框架加、**不进模型面路径**）。
⚠️ **三项不是互斥的**——§3.2e 推荐的 **(c) 正是把第 2 项与第 3 项按方向拆开**：**写**侧走第 3 项
（写入者段由框架加、**不进模型面写路径**），**读**侧走第 2 项（跨格读回来的条目**必须**带写入者段
才定位得回）。**别把第 2 项整条否掉。**

**⟹ 动手前定**（⚠️ **调研已做，但推荐的是下表**没有**的第三项 (c)——见 §3.2e 决策 1**）：

| | (a) 不分区（全落基准 ns）| (b) 读也收窄到自己那一格 | ⭐ **(c) 写收窄 + 读可跨（只读）** |
|---|---|---|---|
| 唯一性 | 靠模型给的路径 | 靠 ns | 靠 ns（写侧） |
| 可改写 | ⚠️ 会分叉 | ✅ | ✅ |
| 成员间可见 | ✅ | ❌ **丢失** | ✅ **保住** |
| 代价 | 靠路径约定分域 | fork / 成员之间互不可见 | **模型面路径要能区分「我的 / 别人的」** |

⚠️ **(a)(b) 是本节初稿列的；(c) 是第 8 轮调研才浮出来的，严格优于 (b)**——见 §3.2e 决策 1。

⚠️ **一个更窄但真实的暴露面**：内部决策 LLM（分类器 / 评估器 / 反馈教练）走 `runDecisionAgent`，
**它不 push 归属槽** ⟹ 写入者维为空 ⟹ 跟**顶层 agent 落同一个基准 ns**。框架已把这条记为已知借用
（「『不进历史』顺带变成『没有记忆身份』」），但它给的出路是「决策 LLM 压根不该写记忆」——**便签是
模型面工具，业务给决策 agent 配上就写了，框架拦不住**。

#### (ii) 租户维——那套规则里**根本没有这一维**

§3.2 原先写的是「可见性**复用**『写入者维进 ns』那套已打磨过的规则」，**现已改成「不能照抄」——本节
就是那个改动的依据**：去读那套规则，它分的是**写入者在编排树里的位置**，跟租户毫无关系：

- `memNS = StoreMemoryNS + 写入者位置`（`basic_agent.go:1817-1821`），基准 ns 是**装配期**的
  `a.config.StoreMemoryNS`，**没有 per-request 覆盖钩子**（对照历史层有 `WithHistoryOwnerFunc`）。
- 而且写入者维**读侧默认不隔离**——同一段代码的注释写得很清楚：「读侧默认不变：注入仍搜基准 ns，
  后代全在里面 ⟹ 同一个基准 ns 下的多个 agent 照旧互相看得见（**那是设计意图**）」。它是**写侧
  收窄的抓手**，不是隔离边界。
- `store` 包本身零 owner 概念。

**为什么这次不能按「业务自己在 ns 里加 tenantID」结案**——**在框架自带的两个多租户前门上业务做
不到**：`agui.AgentFactory func(hooks hook.Hooks) agent_v2.Agent`（`agui/handler.go:69`）**不收
ctx**，工厂拿不到 owner；`a2a/server` 是**单实例 agent 服务全部租户**。而这两个恰恰是刚被强制
`WithOwnerResolver`（不配 panic）的那两处。

**为什么便签比 StoreMemory 更危险**：StoreMemory 今天勉强扛得住，是因为它的内容是 agent 自己的
产出、且**没有模型面的枚举入口**。便签两条都不成立——§3.2 要给「列出」工具，而 `Search` 的语义是
「本 ns + **全部后代**」。叠加 §3.2 第 3 条那句 prompt 政策（不向用户披露便签）和 §3.2b(4) 尚未
拍板的「trace 记不记内容」，**泄漏对两个租户和运维三方都不可见**。

**修法有现成形状，成本近乎为零**（⚠️ **调研已做，推荐「库层不碰 + 平台层 push + 便签 ns 计算处折」的分层做法，见 §3.2e**——⚠️ **别去 `agui`/`a2a/server` 里找「折」的位置，那儿只 push**）：ns 由框架折入 `compose_v2.GetOwner(ctx)`，照
`handoff_agent.go:729-733` 那个已打磨过的写法——**owner 为空时 ns 形状逐字不变**（不是「多一个
空段」，那会让既有存档一次性失联）：

```go
if owner == "" { return store.NS(base, name, threadID) }
return store.NS(base, name, owner, threadID)
```

⚠️ **同一处根因，goal（§4）的爆炸半径更大**：§4 全节一处 owner 字样都没有，而 §4.4 第一条就是
「`store.Store` 里一条目标记录」。便签泄漏 = 读到别人的文本；**目标记录泄漏 = B 租户的 agent 去追
A 租户的 objective**，而这套东西的产出按 §4.1 就是「满足条件时再自动跑一轮」= **自动烧钱**；且
「已跑轮数 / 上限」与 objective 在**同一条记录**里 ⟹ **跨租户共享一个预算池**，A 能耗尽 B 的配额，
或反过来给自己续命——与 §4.4「模型没资格给自己解封」的设计意图直接冲突。

> ✅ **一条正面结论，免得实施时过度设计**：「进程内已授权标志」若放 `RunSession`，**那一层天然
> 有 owner 维**（`agui` 的 `sessionKey{owner, threadID}` 两维不拼串；`a2a/server` 的
> `taskKey{owner, taskID}`）。所以 §4.4 已列的两个坑（`NextTask()` 保留 values / 子会话共享
> values 指针）**就是仅有的两个**，不必再补租户维。

### 3.2d ⚠️ MED：key 由模型给，而 `store.Store` 对 key **零契约**——后端已经分叉了

§3.2 明写便签的「key 是**模型给的便签路径**」。查下来：**`store.Store` 只校验 ns**
（`Namespace.Validate()`），**key 没有任何校验入口**，而三个后端对「空 key」的行为已经不一致——
`redis` **拒绝**（`redis/store.go:77/173/221` 三处 `key == ""` 守卫），`sql` 与 `InMemoryStore`
**零校验直接接受**。`store/conformance` 的 ns 维覆盖到 dot / NUL / 空段 / 兄弟前缀，**key 维一条
都没有**。

今天不成问题，是因为 key 全是**框架铸的**。**模型一接手，这个未定义契约就默认可达**——典型症状是
「一期用 `InMemoryStore` 开发全绿、上线换 Redis 才炸」。

⟹ 便签这层要给 key 定**字符集 + 长度上限**（§3.2 第 2 条本来就要求「把上限告诉模型」），并把 key
维**补进 `store/conformance`**。

> ✅ **查过但不存在，别去加防御**：**路径穿越不成立**——ns 是外层 map key、key 是内层，两维不
> 相通；`sql` 走绑定参数；`redis` 把 ns 拼在 key **左边**，往 key 里追加任何东西都改不了前缀。
> 实测 `../../etc/passwd` / `note/../../other` / 含 NUL 作 key 都只是普通 key，读不到别的 ns。

#### 决策 1（ns 分区）—— ✅ **已决 (c) 写收窄 + 读可跨（只读）**（2026-08-27）

⚠️ **本节的论证在第 11 轮被部分推翻，结论幸存但理由已换——以 §0 为准。**

**关键发现：可改写性与作用域是绑定的。** A 家同一个产品里有**两套**便签，工具集不同：

| | **写**的作用域 | **读**的作用域 | 写类工具 | 能不能改 |
|---|---|---|---|---|
| 线程便签 | **限当前线程** | ⚠️ **可跨线程**（绝对路径） | 有 `append` + `write`（覆盖）| ✅ 随便改 |
| 全局记忆 | 跨线程共享 | 跨线程共享 | **只有一个 create-only 的「加一条」** | ❌ **无 edit / delete**，撞名 O_EXCL 硬失败 |

> ⚠️ **第 8 轮订正：初稿把线程便签写成「当前线程独占」，读侧不成立。** 原文是
> 「相对路径属于当前线程；**绝对路径可以读其他线程的便签**，但写限于当前线程」——初稿引用时
> **省掉了中间那个从句，而那正是反证**。

**订正后的规律更锋利**：**可改写性取决于「写」是否独占，与「读」收不收窄无关**。真正的修改在共享
侧交给一个**持全局锁的离线整理环节**串行做；连「忘掉这件事」「更新那条」在共享侧也是**再写一条新
记录**。

⭐ **而分叉在那家是被「路径形态」消解的**，不是被「读收窄」消解的：相对路径 = 我的（可写），
绝对路径 = 别人的（只读）⟹ **「改别人的」这个动作在结构上不存在**，模型不必也无法把读来的东西
写回错的格子。

**「读合并 → 改 → 写回来源那格」有两类答案**：

- **拒绝合流**（多数）：一处的容器类型 docstring 逐字写着「检索搜全部，**写在只读模式下是 no-op**」
  （非只读时 scope 是**必填位置参数、无默认**）；另一处的权限层同一个答案——**读三层合并、写有一个显式的
  「落哪一层」枚举**（⚠️ 第 8 轮核实：该字段**是可选的**，不是强制必填；初稿写「必须」过强）。
- ⚠️ **但确实有一家做了自动写回——初稿写「七仓零命中」是错的**（第 8 轮独立找反例揪出）：
  同一家的记忆写入流水线上，模型调「记住」工具**不给 scope** → **跨全部 scope 检索** → 一个 LLM
  决定要不要 update 既有记录 → 写回时 **`scope = existing.scope`（照抄来源那一格）**，调用方和模型
  全程没说过 scope；工具描述里也明写「**系统推断 scope**」。

⚠️ **但这个反例不支持「让模型读合并后自己改」**——它的写回决策由**框架 + 一个分析 LLM 接管**
（按主键 update），模型**连键都不给**。⟹ **「不做形状 A」这个结论仍成立，论据要换**：形状 A 需要一个
**框架侧的写回仲裁**（谁来决定 update 哪条），那是「另一套机制」、不在一期范围。⚠️ **(b) 和 (c) 都
不需要它**——本节最终推荐的是 **(c)**，见下。

⚠️ 精确限定：**在「作用域 = 带优先级的配置覆盖层」范围内，「自动回源」七仓零命中**——多层配置
**一律硬编码写用户层**，其中一家还把「写回来源层」**显式否决并记录在案**（理由：那会把用户偏好绑死
在某一份组合文件上，而用户层必须能跨模板升级存活）。放宽到「任意多分区读写空间」就不成立了。

**⟹ 推荐从 (b) 改成一个第 8 轮才浮出来的第三选项：(c) 写收窄 + 读可跨但只读。**

| | 写 | 读 | 可改写 | 成员间可见 |
|---|---|---|---|---|
| (a) 不分区 | 全局 | 全局 | ⚠️ 会分叉 | ✅ |
| (b) 读写都收窄 | 自己那格 | 自己那格 | ✅ | ❌ **丢失** |
| ⭐ **(c) 写收窄 + 读可跨（只读）** | 自己那格 | 可跨格 | ✅ | ✅ **保住** |

**(c) 同时拿到 (a) 的可见性和 (b) 的可改写性**，代价是**模型面路径要能区分「我的」和「别人的」**
（那家用相对 / 绝对，我们可以用一个显式前缀或一个独立的「读别人的」工具）。

> ✅ **可行性已核（第 9 轮）：(c) 在现有 `store.Store` 上零改动可实现。** `Item` 同时带
> `Namespace` 和 `Key`，而 `Search` 是**前缀**语义 ⟹ 跨格读回来的每条都自带完整定位，
> 再用 `Get(item.Namespace, item.Key)` **精确读得回**。映射：
> - **写** → `Put(自己那格, 模型给的 key)`，写入者段由框架加、**不进模型面路径**；
> - **跨格读** → `Search(基准 ns)`，框架把别人的条目渲染成**带写入者段的路径**（＝「绝对路径」）；
> - **精确读回** → `Get(那条自带的 ns, key)`。
>
> ⟹ **写工具只接受不含写入者段的路径**（必落自己那格），**含写入者段的路径只有读工具认** ——
> 「改别人的」在**接口形状上就不存在**，与那家用相对/绝对做的区分是同一个机制。
>
> ⚠️ **仍有一个坑照旧**（§3.2c(i) 已记）：`Get` 对不存在返 `(nil, nil)` **不返错** ⟹ 模型
> 读一条**已被别人删掉**的便签会拿到**静默空**。读工具要把「没有这条」和「内容为空」区分开。

⟹ **本文原先推荐 (b) 是因为只看到两个选项；(c) 严格更优，除非那个路径区分做不出来。**

⚠️ 无论选哪个，**§3.1「模型要能改、能删、能重写」的前提是「写独占」**——这一条不变。
**跨写入者共享那个空间一期不做**——真要做，它是**另一套工具 + append-only + 离线合并**，不是把
现在这套放宽。

> ⚠️ **(b) 和 (c) 都关不掉 §3.2c(i) 末尾那个「更窄的暴露面」，别以为选了就全好了。** 那条说的是
> 内部决策 LLM 走 `runDecisionAgent` **不 push 归属槽** ⟹ 写入者维为空；而**顶层 agent 的写入者维
> 同样为空** ⟹ 两者「自己那一格」**是同一格**（都是基准 ns）。收窄读侧只解决「br1 读到 br2」那类
> 分叉，**解决不了这一条**。要关它得另外动手（给决策 LLM 一个独有的写入者段，或干脆不给它们注册
> 便签工具）。⚠️ **对 (c) 同样成立**——(c) 的写侧收窄与 (b) 一样，而这条洞出在**两者的写入者维
> 都为空**，跟读侧放不放宽无关。

#### 决策 2（索引注入）—— ✅ **已决：不注入索引**（2026-08-27）

⚠️ **本节列的两条理由（「4:1 主流不注入」「触发时机模型察觉得到」）第 11 轮实测后都是错的。结论未变但理由全换，以 §0 为准。** 本节保留作对照。

**分野不在厂商，在「被索引的东西有没有界」**：

| 被索引的东西 | 做法 | 谁 |
|---|---|---|
| **开放式便签**（无上界、模型自己写）| ⚠️ **初稿写「多数不注入」，第 11 轮重数后是反的** | 见下 |
| 同上 | ⚠️ **但有一个反例，而且它是最贴近我们要做的那个东西** | 见下 |
| 有界的外部预定义集合（如 skill 清单）| 注入 name + description + 预算 + 分级降级 | 多家一致 |

实测确认：A 家的 prompt 模板里**便签相关字样零命中**——模型靠**工具可用性 + 一段静态 guidance**
知道有便签，**不靠索引**。

**新鲜度问题主流怎么解？不是每轮重注**，而是「**按内容 digest 差分注入 + 检测到被压缩吃掉后重发**」，
理由都指向同一个：**KV cache 前缀复用**（每轮重注会打断可复用前缀）。另有一家的写工具**当场重建索引
并把新记录塞进 tool_result**——模型根本不必等下一轮注入。

> ⚠️ **第 8 轮订正：「开放式便签一律不注入」是错的，同一家就有反例。** 那家的**文件式记忆
> provider**（模型自由命名文件、无上界，与我们要做的东西**最像**）**确实注入索引**——godoc 逐字
> 「维护一份 `memories.md` 索引并**注入 agent 的上下文**，好让模型知道已经有哪些记忆」，
> 索引**上限 50 条**。它跟本表另一行那个「不注入」的 provider **是并排的两个类**。
>
> **它怎么解新鲜度**（⚠️ **第 9 轮订正：初稿把同一家两个并排 provider 的行为混成了一份，
> 拼出了一个「谁都没有」的组合**）。**属于那个开放式 provider 自己的**只有三件：
> ① **每次写 / 删工具调用后当场重建索引**；② 注入是**每次 run 一次**（不是每次 LLM 调用）；
> ③ 另给一个**现算现返**的列举工具。
> ⚠️ 而「**写工具回吐新记录**」和「instruction 里那句**别假设每个条目都已加载**」**属于它旁边那个
> 主题式 provider**——开放式那个的写工具**只返一句 `File 'x' written.`**，实测其文件里连
> `assume` 这个词都零命中。
>
> ⟹ **修正后的门槛反而更低**：要注入，需要的是**写/删后当场重建索引 + 一个现算的列举工具**；
> 「写工具回吐新状态」**不是必需**（那家的开放式 provider 就没做）。

> ⚠️ **第 11 轮订正：那个「4:1 不注入」的统计是错的，方向也反了。** 重数原因有二：
> ① **按「家」数而不是按机制数**；② **把两类性质相反的东西混成了一类**——「内容其实还在
> 上下文里」（模型自己的 tool_call 参数还在）和「真的什么都没有」，我都记成了「不注入」。
> 另有两家实际注入却被我记反。**按机制重数约 9 注入 : 1 就地指针 : 1 已在历史 : 2 不注入。**
>
> ⚠️ **但只数「模型自己写的、无界增长的」**（那几个 skill 清单是只读语料、不同构），
> **做注目录的只有两家，且两家都给索引加了硬上限**（50 条 / 200 行×150 字符）——它们是
> 离我们最近的先例。

**⟹ 结论仍是不注入，但理由全换成 §0 那条判别式（需要时去查 vs 不查也必须生效）+ 三个前提。** 便签属于「无上界、模型自己写」
那一类，多数不注入；而要注入就得连带把上面那四件配齐（重建 + 每 run 注 + 现算 list + 那句
instruction），**那是更大的一期**。这直接**取消**了 preamble-vs-transient
这道题，连同 §3.2 索引条选项 (b) 要求的那个**压缩 marker**（都不注入了，也就无所谓被压缩吃掉）。

> ⚠️ **但它不取消 §3.2b(1)，反而让那条变重——初稿这里写「顺带取消 §3.2b(1) 整条」是错的，方向反了。**
> §3.2b(1) 讲的是**读便签的 `tool_result` 在上下文里永久累积**（便签工具不在压缩白名单里），
> 跟「注不注入索引」**是两件事**。而不注入索引之后，模型发现便签只能**靠调 `list` / `search`**，
> 那些调用的结果**同样累积** ⟹ **调用次数变多、累积更快**。
> ⟹ **采纳决策 2 的话，§3.2b(1) 的对策必须同时定下来**，否则省下的注入体量会从 tool_result 那头
> 长回来。⚠️ **但两条对策治的不是同一维，别只挑 ①**：设累积量 = N（调用次数）× B（单次体量），
> **① 只压 B、压不了 N**（10 次有界读仍是 10 份）；**只有 ② 能随轮次把旧副本清掉**，即压 N。
> 而决策 2 恰恰是**把 N 推高**的那个改动 ⟹ **② 是主，① 是补**。
> ⚠️ ② 与 §3.2 那条命名约束不矛盾：那条禁的是**误撞**默认白名单（进了却没配套「模型必须能重读」
> 的工具描述），② 是**显式 opt-in 并配齐那份描述**。

⚠️ **代价要认**：有一家把它写进了自己的 prompt——检索是「自动挑选、**可能不完整**」，遇到「有多少 /
列出全部 / 合计」这类问题**必须**换几个 query 反复搜。**我们比它多一件 `list` 工具**，这个代价小得多。

#### 决策 3（租户维）—— ✅ **已决：分层做**（2026-08-27）

| 层 | 谁给身份 | 框架做什么 |
|---|---|---|
| **库层**（调研覆盖的 8 家）| 调用方 | ⚠️ **初稿写「不认识身份」是错的**——**有 typed 身份槽**（见下），但**存储层不消费**它 |
| **平台 / 宿主层** | **平台注入**（HTTP header / 认证中间件）| **自动折进存储路径**，调用方绕不过（⚠️ **仅会话维成立**）|

一家图编排 SDK 的官方立场原文（在它自己的测试注释里）：「**调用方靠 namespace 隔离租户**」——而那句话
出现的语境本身就是代价的证明：正因为调用方拿 namespace 当租户边界，前缀匹配才**必须在段边界停**，
否则 `("u","1")` 会读到 `("u","12")`；这个 bug 他们上个月才修。

> ⚠️ **第 8 轮订正：「库层不认识身份」是错的，但订正后反而更支持本节的推荐。** 库层实际有两处
> typed 身份槽：(1) 一家图编排 SDK 的运行时上下文里有一个 **typed 的 `user` 字段**，且**解析逻辑
> 就在 OSS 库里**（从 config 里认那个 authenticated-user 键）——只是它的 docstring 自承「平常由
> Server 填」，而且**没有任何存储代码读它**（纯观测面）；(2) 另一家的记忆记录上有 `source` +
> `private` 两个字段，**框架自己执行可见性裁决**（非公开记录只对同 source 的检索可见）。
>
> ⟹ **精确表述是「库层有身份槽、但存储层不消费它」**，而不是「库层没有身份概念」。
> **这恰恰是本节推荐的形状**：我们的 `compose_v2.GetOwner(ctx)` 就是那个槽，而我们提议**让便签的
> ns 计算处真正去消费它**——比 (1) 更进一步、又不像 (2) 那样把裁决塞进存储层。
> ⚠️ (2) 的弱点必须避开：它的 `source` 是**调用方自报、无认证**，而且有一个 `include_private=True`
> 能整体绕过 ⟹ **那是「身份维度」不是「租户隔离」**。我们的 owner 来自宿主的认证中间件，别退化成自报。

⚠️ **另一条反直觉的**：确实有一家「自动折了一维进 namespace」，但折的是**生产者身份**（哪个编排 /
哪个角色写的），**不是调用方身份**。**那恰好就是 crew-go 现在的形状**——我们在生产者维上与业内一致，
**缺的那一维在库层是全行业空白**：「自动折」的那个位置早被「谁写的」占了。

而做了自动折的那家在**宿主层**：从 HTTP header 抬进 request-scoped 上下文，再折进存储路径。
⚠️ **但第 8 轮核实发现这里要拆成两条链，初稿混成了一条**：
- **会话维那条**（按「哪次对话」折）**确实 fail-closed**——注释逐字「没有 key 就没法按会话分区，
  **宁可跳过持久化也不污染那个共享桶**」。
- **用户维那条**在**另一个包**里，用的是**另一个 header**，而且**不是 fail-closed**（缺 user id
  时回落成无 scope 的布局）。更要紧的是：那个宿主包里**「用户维 key」在生产代码里零消费者**
  （只出现在它自己的定义和测试里）。

⟹ **别把「业内已经端到端做好了用户维自动折 + fail-closed」当既成事实**——**会话维做好了、
用户维没有**。我们要做的那件事，业内先例比初稿写的要弱。

**⟹ 推荐分层**（⚠️ **「谁 push」和「谁折」是两件事，初稿写混了，已订正**）：
- `store.Store` **库层不碰身份**（与业内一致，也不破接口）；
- **身份由平台层 push 进 ctx**——`agui` / `a2a/server` 已强制 `WithOwnerResolver` 并且**已经在做这件事**
  （`agui/handler.go:301` / `a2a/server/interceptor.go:154` / `executor.go:251` 都是
  `compose_v2.WithOwner(ctx, owner)`）；
- **折入在便签的 ns 计算处**读 `compose_v2.GetOwner(ctx)` 完成——形状照 `handoff_agent.go:646/783/793`
  调 `handoffActiveNS(name, GetOwner(ctx), tid)` 那套，**owner 为空时 ns 逐字不变**。

> ⚠️ **为什么这个区分要紧**：照初稿字面去 `agui` / `a2a/server` 里找「折」的位置**根本找不到**
> （它们不计算便签 ns，只 push）；而且**纯库用法**（`BasicAgent` + 便签，不经这两个宿主）
> 那条路**没有任何人折**。放在 ns 计算处则三条路径统一生效，owner 为空时退化成今天的形状。

⚠️ **另有一个第三形状值得一并考虑**（它顺带能解 §3.2d 的「key 零契约」）：把身份做成 key 类型里的
**一个独立字段**（结构化而非拼串）+ 单租户默认值 + 用 **conformance 套盯后端**。结构化的好处是
**不存在前缀撞兄弟**那类问题；代价是**有默认值就不能 fail-fast**，多租户忘了设不报错、静默合桶。

#### 采纳后对一期范围的影响（**动手前先看这条**）

采纳决策 2 后方案会**显著变小**：压缩 marker、索引预算与降级、preamble-vs-transient 那道题全部不需要。
一期从「列 / 读 / 写 + 索引注入」缩成 **三个工具（列出 / 读 / 写）+ 一段静态 guidance**——工具数对账与「为什么砍追加」见 §6。
⚠️ **但 §3.2b(1) 不在被取消之列**（它是 tool_result 累积，与索引无关，且因调用变多而**变重**）——
一期仍须为它选一条对策。
⚠️ 这与 §5「补入口而不是建子系统」的判据是同向的——**变小是信号不是损失**。

### 3.3 历史检索——缓做，且必须是 opt-in

**先说为什么缓**：两家最成熟的实现最后都把它**默认关掉了**——一家造完 4 个包 + 完整文档后，三个
发行组合全部不挂它、全文索引默认不开，理由是「附带教了一套没人要的先前工作检索流程」；另一家用
三重开关 gate 到只有自家托管账号可用。**造得出来不等于该默认开。**

**缺口是有界读**。现在：

```go
Append(ctx, key, msgs) error
Load(ctx, key) ([]*schema.Message, error)   // 返回整条会话，喂不进模型
```

要加检索与有界读，**就要改 `HistoryStore` 接口 = 改所有业务自研 backend = 改 `history_conformance`
套**。所以**先定对形状比先写出来重要**。

**形状定下来时，这五条建议值得参考**（每条都有外部踩坑依据）。⚠️ **但别直接照抄理由**——
外部的论证依赖它们自己的机制，第 1、2、5 条的前提在我们这儿**都不成立**，见各条的 ⚠️：

1. **不给模型游标 / 分页 / limit**——**结论照抄，理由要换**。外部的论证是「模型翻页会写日志、
   推进 generation、游标随即失效」；⚠️ **那个前提我们没有**（`agent_v2/history.go` 全文无
   generation / revision / 版本概念）。**我们自己的理由更硬**：历史写入是**单 worker 异步**的
   （`historyWriter`），而 `closeAndJoin` 在 **Run 出口**才 join ⟹ 一次 Run 进行中，本轮乃至前几轮
   的历史**可能还在队列里没落盘**，翻页结果本就不稳定。替代做法相同：一次调用内部翻到上限为止，
   满了就告诉模型「缩小查询范围」。
2. **`Owner` 绝不从模型入参取**。我们已经预演过这个结论——`HistoryKey.Owner` 必填无默认，godoc
   写着「ConvID 来自 wire，是**续接标识符不是授权令牌**」，**不必新造授权层**。⚠️ **但别照初稿那句
   「用写入器持有的那份**配置**」做——那句已过期，照做会复现一个刚修完的跨租户越权。**
   `historyConfig.resolveOwner`（`agent_v2/history.go:238-250`）是**三档**：`ownerFunc` →
   **`compose_v2.GetOwner(ctx)`** → 静态 owner。中间那档是后加的，它修的正是「业务接
   `agui.WithOwnerResolver` 做多租户、又照 godoc 写 `WithHistory(hs, "prod")`，于是两个租户的
   对话全落进一个分区」。⟹ 工具要调的是**写入器的 `resolveOwner(ctx)`**，不是读它的静态字段。
   （`historyOwner()` 返回的是**归属槽 / agent 名**，是另一回事——这条仍然对。）
3. **搜自己这条会话时，截止到发起本次调用的那一步之前**——否则模型会搜到自己刚写下的 query。
4. **检索工具独占一个超步**——⚠️ 理由**不同于** §3.2 第 1 条（那条是「写要串行」）：一次检索
   内部会消费掉 generation 绑定的游标，故不能与兄弟工具并行；而**精确读 / 追溯类工具不在此列**
   （外部明确把它们放回并行）。这条与第 1 条「不给游标」是同一个根因。
5. **截断不在这个工具里做**。外部的理由是「在这里做会与 harness 级的统一溢出策略重复，并让检索
   工具与别的工具行为不一致」。⚠️ **那个前提我们没有**——全仓无统一溢出机制（`spill` 零命中），
   所以这条**现在不能照抄**：要么先立一个跨工具的统一截断策略再遵守它，要么就在工具里做但**明确
   记一笔「这是权宜，将来有统一策略时要收回」**。别默认外部的分工在我们这儿已经存在。

⚠️ **还有一条外部有、我们必须自己面对的差异：一致性。** A 家在同一个 crate 里给两种保证——
history 标 **eventually consistent**（「新产生的条目可能要几秒才出现」），notes 标 **strongly
consistent**，因为前者是派生索引、后者是模型直写。**我们同样是两种，但成因不同**：便签落
`store.Store` 是**同步 Put**（强一致），而历史走**异步写入器**（最终一致，且窗口一直开到 Run 出口
join）。⟹ **检索工具的描述里必须把这条告诉模型**，否则它会以为「刚说过的话立刻搜得到」。

**实现路径**：检索**放进 `HistoryStore` 接口让后端自己实现**（PG 用全文索引、Redis 用检索模块），
框架只提供一个朴素的内存扫描默认实现。⚠️ 外部那套单进程本地索引**对我们不适用**——我们的 backend
是业务自研的 Redis/PG，多副本部署是常态。

## 4. goal——不作为一个 feature 做，拆成三件小事

**核心判断：goal 里真正稀缺的东西只有两条，而它们各自独立、都很小；「循环」本身我们已经有了。**

### 4.1 ⚠️ 硬约束：活性不能持久化

这是本文**最重要的一条硬约束**（另有一条前提见 §4.3：目标记录怎么传到 `ExitCondition`——那是可选路径问题，本条是安全问题）。

外部的做法是把状态拆成两个轴：

| | 持久 | **进程内，永不持久化** |
|---|---|---|
| 回答 | 目标是什么、处于什么阶段 | **可不可以再自动跑一轮** |

任何「会话开始」的边沿都把后者打回未激活；插件挂到既有 agent 上时**绝不继承**活性。要恢复自动跑，
**必须有一次人显式授权**。

**为什么这条对我们尤其致命**：我们的 cp 会在 Run 出口存档、入口 auto-load 捡起。如果目标状态跟着
cp 一起持久化、而「可不可以再跑」也在里面，那么**进程重启 / 存档被捡起 = 自主循环自己醒过来开始
烧钱**。

⟹ **持久的只有「目标是什么、什么阶段」；「可不可以再跑一轮」永远是进程内的，且必须由一次显式的
人类动作重新点亮。**

### 4.2 预算用轮数，不用 token

外部一家用 token + 时间预算，为此付出了独立记账模块 + 两把信号量 + 一套 CAS + 六个状态；另一家用
**轮数**，几十行搞定。后者还避开了「跨 provider 的 token 统计不准」这一整个雷区。

轮数预算跟 `MaxRounds` / `MaxIterationsError` / `maxVisit` **同族**（都是数轮次而非数 token）。
⚠️ 但**计数器要自己一个**——那三个都是**无差别计数**（`loopAgentRoundCh` 是 `Sum`，body 节点每跑
一轮无条件 +1；`maxVisit` 按 NodeID 数访问次数），**没有一个能区分「这一轮是不是目标驱动的」**，
表达不了下面那条 ⚠️。真正的落点是 §4.4 那条目标记录里的「已跑轮数 / 上限」。

⚠️ 配套一条：**只有目标驱动的那些轮次消费预算**——人类插话、澄清、以及不相关的工作不该吃配额。

> ⚠️ **HIGH：这条要求现在没有承载者，初稿把它写得像已定，实际是个开口。** 逐条对：
> - **模型不能数**——§4.4 明写「更新只准模型设『完成』和『受阻』」（理由是模型没资格给自己解封）。
>   让它数轮数等于让它能给自己续命。
> - **`ExitCondition` 数不了**——它的全部入参是
>   `(ctx, lastOutput *schema.Message, round int)`（`loop_builder.go:41`，调用点 `:225`）。
>   `lastOutput` 是最后一条 assistant 消息，**看不出这一轮是目标驱动还是人类插了一句**。
> - **现有那个计数器更不行**——`loopAgentRoundCh` 是 `Sum`（`loop_builder.go:62`），body 每跑一轮
>   无条件 `Write(…, 1)`（`:179`），本来就是无差别计数。
>
> ⟹ **要么放弃这条区分**（预算退化成「总轮数」，接受人类插话也吃配额），**要么先定谁来打标**
> ——判断「这一轮是不是目标驱动」的信息在**进入这一轮之前**就该确定（是谁触发了这一轮），
> 而不是从产出里反推。动手前必须选一个。

### 4.3 循环用现成的 `LoopAgent`

外部那个「空闲时自动开新一轮」的动作，本质是**给一个没有循环原语的 CLI 补一个循环**。我们不缺循环：

```go
type LoopAgentExitCondition func(ctx context.Context, lastOutput *schema.Message, round int) (bool, error)
```

它经 `WithLoopExitCondition` 装配，且已经过 cp / Resume / 嵌套的全套考验。

**我们缺的不是循环，是循环携带的那份持久目标和它的授权闸。**

⚠️ **一个必须写明的前提**：`basic_agent.go` 的 godoc 写着「**8 编排 wrapper 自身不持 / 不 push**
store ctx」（by design）——所以 `ExitCondition` 拿到的 ctx 里**有没有 `store.Store` 取决于业务**
（业务在外层调过 `store.WithContext(ctx, st)`，或由父 BasicAgent 的注入透传下来）。⟹ 方案要么
要求业务在外层放 store，要么让目标记录经**装配期**传给 `ExitCondition` 的闭包，而不是指望从 ctx 拿。

### 4.4 所以 goal 在 crew-go 应该长这样

- `store.Store` 里一条目标记录：objective + 阶段 + 已跑轮数 / 上限

> ⚠️ **HIGH：初稿这里写的是「+ 一个版本号做 CAS」——那是抄了外部的形状没核我们的地基，已删。**
> `store.Store` 接口六个方法（`store/store.go`）**没有任何条件写 / CAS / 版本语义**，`Put` 是
> **无条件覆盖**；`Batch` 是 **best-effort per-Op 错误隔离**，而且那是**唯一**合法语义——
> godoc 明写「别做成单事务原子写」，conformance 钉着（2026-09-07 `d6d06312`；此前那句
> 「后端**可**优化为单事务原子写」的邀请已删）。
>
> ⟹ 想要 CAS 只有两条路，**两条都得先拍板**：
> - **给 `store.Store` 加条件写方法**——那是**破接口契约**，所有业务自研后端 + `store/conformance`
>   套都要跟着改。⚠️ **这正是本文 §6 把历史检索排到最后一期的那个理由**，goal 这边不能当它不存在。
> - **接受非原子的 read-modify-write**——那就别在文档里写「CAS」。此时要说清**谁会并发写**：
>   tools 节点在 `len(toolCalls) >= 2` 时**并发**跑（ISSUE-81），模型一轮里发两个 `update_goal`
>   就撞；`LoopAgent` 的 body 若是 `ParallelAgent`，各分支也会同时写同一条目标记录。
- 三个模型面工具：读 / 建 / 更新，其中**更新只准模型设「完成」和「受阻」**——暂停、恢复、超限这些
  由人或系统控制（外部两家都这么切，理由是模型没有资格给自己解封）
- 一个**进程内**的「已授权」标志（§4.1）
- `LoopAgent` 的 `ExitCondition` 读它

**不需要新的编排 / 循环原语。**

⚠️ 但**别读成「比 notes 更便宜」**：那三个模型面工具跟 notes 的工具是同一类东西，§3.2 那份改动面
（新常量 + 工具定义 + 名单 + Option 注册点 + 写类工具的 memo 问题）**逐条同样适用**，而且
`create_goal` / `update_goal` 都是写类。另外两处落点还没定：**「进程内已授权标志」放哪个现有结构**——⚠️ **`RunSession` 的 KV 看似合适，实测有两个坑，
两个都让「活性」泄漏得比预期广**：(a) `NextTask()` **只换 `RunID`、values 原样保留**
（`session.go:192-194`）⟹ 换任务默认**继承**活性，与 §4.1 的硬约束正好相反；(b) 子会话是
**半共享**的——`values` map 与父**共享指针**（`session.go:196-198`）⟹ 父点亮的活性会**直接对所有
子 agent 可见**。两条都要显式处理（换任务时主动清、或干脆不放 KV 而放一个不随会话传播的载体）；以及 §4.3 那条 store ctx 前提、上面那条 CAS 的二选一。**改动面只会比 notes 大。**

### 4.5 三条外部主动列出的局限，我们会一样踩

1. **没有独立评判者**——「是不是真完成」「是不是同一个阻塞」全靠模型自己判，运行时只能机械地数
   「连续几轮」。
2. **轮数不是资源预算**——token / 钱 / 时间 / 配额是另一套策略，不映射成目标的阻塞原因。
3. **异常不自动重试**——瞬时的 provider / 持久化故障应当要求人授权恢复，不做隐式重试。

⚠️ 另有两段 prompt 措辞值得连同机制一起抄：**把「完成」默认视为未经证明**（不确定或间接的证据一律
按未完成处理，审计必须**证明**完成，而不只是「没找到明显剩余工作」）；**报「受阻」要连续若干轮遇到
同一阻塞条件**才准，人恢复之后重新计数。这两段直接对着「模型提前宣布完成」和「一遇障碍就撂挑子」
两个真实失败模式。

## 5. 先回答一个反对意见：按我们自己的判据，这方案该不该做？

**必须正面回应，因为它跟本仓刚做过的一次决策直接冲突。** 重估 todo 时定的判据是「**产品层 /
SDK 层的分野**」——内置的都是产品、不内置的都是 SDK，我们是 SDK，故 defer。

把同一把尺子量「自我追踪」，**本轮核实的分布一模一样**：

| 层 | 有没有 |
|---|---|
| A 家（产品）| ✅ notes + 历史检索工具 |
| C 家 harness（产品）| ✅ 两套记忆 provider |
| B 家（产品）| △ 无独立层（共享工作区即记忆）|
| 三家 **SDK** | ❌ **全无**——其一的 memory 命中是「指令文件配置」；其一的 memory 是**会话存储**（对等我们的 `HistoryStore`）、notes 命中全是文档小标题；其一零命中 |

⟹ **按那把尺子，这方案该 defer。** 装作没这回事是不诚实的。

**但有一条差异，它改变的是结论的形状而不是判据本身**：三家 SDK 缺的是**地基**——它们没有
`store.Store` 这种通用 KV + 检索层（对等物只到「会话消息存储」为止）。**我们有**（494 行 + 语义

所以正确的结论不是「做」或「不做」，是**做什么形态**：

- ❌ **不该做**：一套完整的、默认开的便签子系统——那是产品层的活，且两家最成熟的同类实现都把它
  默认关掉了（§3.3 已记）
- ✅ **该做**：把**已有地基**的最后一段路补上——`store.Store` 已经在那儿、offload 已经在写它，
  缺的只是**给模型的入口**。这是「补全已有能力」，不是「新建一个子系统」
- ⟹ **必须 opt-in、必须默认关**，与 §3.3 对历史检索的结论一致

⚠️ **一条留给未来的判据**：如果实施时发现「补入口」膨胀成了「建子系统」（开始需要自己的索引、
后台整合任务、独立存储层），**那是判据在提示这条越界了**——应停下来重估，而不是继续做大。
